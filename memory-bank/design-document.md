## 1. 产品定位

### 1.1 一句话定位

**在国外，喊一声就有人。** 喊呗是一个面向海外旅行者与当地华人/留学生的"异地找人"平台：旅行者把落地后的具体需求喊出来，当地人顺路接下来。

### 1.2 定位修正：V1.0 → V2.0

| 维度 | V1.0「同路人」 | V2.0「喊呗」 |
|---|---|---|
| 产品本质 | 海外旅行搭子社区 | 海外旅行场景下的异地求助撮合平台 |
| 原子单位 | 帖子（内容） | 需求单（Request，可被接、可闭环、可评价） |
| 需求范围 | 找搭子为主 | 搭子同行、付费地陪、借物易物、住宿、打听咨询、代购跑腿、翻译陪同、应急求助 |
| 城市社区角色 | 内容分区 | **供给容器**：当地先有人入驻，才有能力承接需求 |
| 信任机制 | 身份标签 + 举报 | 四层信任体系 + 双向评价 + 履约信用分 |
| 交易机制 | 口号写了担保交易，功能未实现 | **明确不碰资金**：平台托管"约定单"而非托管钱 |
| 冷启动兜底 | 无（发了没人理就流失） | AI 助手小螺作为供给的兜底层 |
| 商业化 | 未定义 | 四阶段路线，起点是会员与曝光，终点是本地商家生态 |

一句话概括这次修正：**V1.0 想做的是"社区带出交易"，V2.0 做的是"需求驱动社区"。** 内容仍然重要，但它的职责从"主线"变成"供给端的入驻理由和 AI 兜底的知识来源"。

### 1.3 命名与品牌

**最终定名：喊呗**（备选评估见附录 A）。

选择理由：

1. **语义直白**。"喊"精确对应产品的核心动作——需求方主动喊人。用户第一次听到名字就知道这是干什么的，零教育成本。这对一个零预算、靠自然口碑传播的项目是决定性的。
2. **可动词化**。"上喊呗喊一个""喊呗上喊个搭子"——品牌名本身就是行为召唤（CTA as brand name），传播链条最短。这是"滴滴"这类名字成功的同一机制。
3. **搜索独特性高**。语气词组合独特，在微信小程序搜索与社媒搜索中不易被淹没。
4. **语气亲和**。"呗"带来随意、轻松、不欠人情的语感，正好降低"向陌生人求助"的心理门槛——这是本产品最大的用户心理阻力。
5. **场景覆盖完整**。喊个搭子、喊人帮带、喊人问路、喊人救急都自然成立，不像"搭子"类命名只能覆盖同行场景。

**"海螺"不作为产品名，但保留为品牌资产。** 海螺作为产品名有三个硬伤：语义不直白（听到"海螺"无法推断产品用途）、无法动词化、以及搜索污染严重（海螺水泥、海螺沟在中文语境中占据绝对认知位置）。此外"海"字指向海岛度假，与本产品的欧美城市场景方向相反。

但"吹响海螺召集同伴"这个意象非常契合产品，因此把它下沉为品牌层资产：

- **AI 助手命名「小螺」**：吹响螺号 = 把你的需求喊出去、传得更远。与 Agent 的分发职能形成语义闭环。
- **吉祥物**：一只吹海螺的小角色，用于空状态、引导页、成功撮合的庆祝动效。
- **品牌故事**：航海时代靠螺号在陌生海岸互相呼应——正是"人在异乡喊一声"的原型。

品牌信息：

- 中文名：喊呗｜英文名：HeyBay
- 英文名释义：`Hey` = 喊一声、打招呼，对应产品核心动作；`Bay` = 港湾、靠岸的地方，接续"螺号在陌生海岸互相呼应"的品牌故事——旅行者落地后的港湾。选 `Hey` 而不选 `Call`，是因为 `call` 在产品语境中易被理解为通话/客服/呼叫中心，与"发需求单"的核心动作语义偏移。
- Slogan：在国外，喊一声就有人
- 英文 Slogan：Holler once, someone's already there.
- 副 Slogan（供给端）：顺路帮个忙，也是一份收入
- 小程序全名（若重名则降级使用）：喊呗 → 喊呗 HeyBay → 喊呗出行
- 代码仓库 / 目录名：`heybay`（不带版本号，版本由 git tag 管理）

### 1.4 业务边界

**做**：欧美城市（首发伦敦）、华语用户、旅行相关的求助与轻服务、微信生态内全流程、信誉担保。

**不做（本期）**：国内同城场景、非旅行品类交易、资金代收代付与提现、复杂清结算、跨境物流。

**明确不做（写入产品原则，长期不做）**：

1. **交友与约会属性**。不做异性筛选、不做颜值展示、不做随机匹配、不做"寻找长期关系"类需求。理由：一旦擦边交友进入，真实求助需求会被淹没，供给端会流失，生态不可逆地变差。治理方案见 4.6。
2. **平台代收资金**。理由见第 9 章合规分析。
3. **AI 全自动代替用户与真人协商见面**。理由见 5.4。
4. **收集与存储身份证件原件**。理由见 4.4。

## 2. 问题定义

### 2.1 V1.0 复盘：14 个待解决问题

这一节是 2.0 全部设计决策的来源。按严重程度分级。

**S 级（阻断产品成立）**

1. **交易闭环缺位**。V1.0 定位写明"免费拼搭子 + 付费租搭子 + 旅行轻交易 + 轻量化担保"，但功能结构中没有任何服务发布、订单、支付、评价模块，"我的订单"仅为预留入口，微信支付标注"后续迭代"。定位与功能严重不匹配。
2. **没有匹配机制**。"搭子出行"只是帖子的一个分区标签，没有结构化行程字段、没有报名/接单动作、没有状态流转。用户发完帖之后，产品不知道发生了什么，也无法衡量成功。
3. **主体资质导致无法上线**。个人主体微信小程序无法获得社交-社区/论坛类目，UGC 发帖、评论、私信是硬性禁区。V1.0 的全部核心功能都落在这个禁区内。详见第 9 章。

**A 级（直接导致社群死水）**

4. **先审后发**。V1.0 规定所有帖子审核通过后才展示。海外用户与国内审核存在时差，一条内容延迟数小时才可见，即时性需求（今天拼饭、现在应急）全部失效。这是"社群死水"最被低估的成因——不是用户不发，是发了看不见、看见了已过期。
5. **反死水规则过于单薄**。仅有"7 天无互动降权 + 小组需有主题内容 + 用户可自建小组"三条。没有冷启动供给方案、没有内容播种、没有需求过期归档、没有小组健康度治理。
6. **用户自建小组无节制**。审核通过即可创建，缺少数量控制、合并与归档机制，结果是把有限流量碎片化成一堆死水小组。
7. **无兜底**。需求无人响应时用户直接流失，且这类流失不可挽回（旅行者在当地只停留几天）。

**B 级（体验与信任缺陷）**

8. **认证机制只有结果没有过程**。身份标签写着"本地华人/留学生/旅行者（已认证显示）"，但没有定义认证依据、材料、审核方式与展示分级。
9. **安全体系缺失**。仅有帖子举报。没有拉黑、没有双向评价、没有信用记录、没有线下见面安全机制。这是一个促成陌生人在异国线下见面的产品，安全不是次要需求。
10. **首页与"组圈"职责重叠**。首页有城市群组选择器与城市筛选，Tab2 又是城市小组入口，两个 Tab 做同一件事，且导图称"定位"、高保真图称"组圈/组队"，命名不统一。
11. **搜索范围不一致**。首页、组圈、我的三处搜索框，可搜范围各不相同（帖子/小组/标签/搭子/地陪/二手），且"地陪""二手"是交易品类却没有交易功能承接。
12. **积分体系有界面无设计**。高保真图存在"签到送积分"banner，功能结构与 PRD 中均无积分体系定义（获取、消耗、价值锚定全部缺失）。

**C 级（可行性与预期问题）**

13. **"同步小红书"不可实现**。小红书没有开放给第三方的内容发布 API，蒲公英类接口仅面向品牌合作方。市面上宣称"一键同步小红书"的产品，实际做法都是**生成文案 + 批量存图到相册 + 引导用户手动打开小红书粘贴**；走私有接口的方案违反平台协议且会封号。2.0 改为诚实的能力命名（见 5.2）。
14. **"本地居民"作为供给端不成立**。非华人本地居民既不使用微信也不阅读中文界面。2.0 明确供给端为华语人群（当地华人、留学生、长期旅居者）。

### 2.2 核心矛盾

把上面 14 条收敛成一句话：**V1.0 建了一个内容社区的容器，却期待它自己长出撮合与交易。**

而撮合是一个密度游戏：单位时间、单位城市内，必须有足够多的"可被响应的具体需求"和"愿意响应的在地供给"相遇。V1.0 的每一个设计选择都在降低这个密度——非结构化的帖子降低了可匹配性，先审后发降低了时效，无节制建组切碎了流量，无兜底让稀疏期的用户直接流失。

2.0 的全部工作可以概括为四件事：**把需求结构化、把审核放快、把流量收拢到城市、在密度不足时用 AI 兜住**。

### 2.3 竞品与差异化

| 竞品 | 用户当前如何解决 | 缺口 |
|---|---|---|
| 小红书 | 发帖找搭子、看攻略 | 无撮合闭环、无身份可信度、私信转化极低、无法按城市沉淀在地供给 |
| 微信群（华人群/校友群/城市群） | 群里喊一句 | 信息瞬时淹没、群主不可控、无信用记录、无法搜索历史、进群门槛 |
| Meetup / Couchsurfing | 参加活动、找沙发主 | 英文环境、以活动而非以需求为单位、华人使用率低 |
| 马蜂窝/穷游/飞猪当地玩乐 | 买标准化地陪/一日游 | 商品化预制产品，无法承接"临时的、具体的、非标的"小需求 |
| 闲鱼 / 华人生活网（如英国 UKPo、加拿大约克论坛） | 二手、租房、跑腿 | 定居者视角，无旅行时效性，界面陈旧，无移动端撮合 |
| 私域"地陪中介" | 微信中介推荐 | 不透明、抽成高、无评价、纠纷无处理 |

**喊呗的差异化定位交叉点**：以"具体需求 + 时效"为单位（区别于内容平台与活动平台），以"在地华语社区"为供给池（区别于标准化商品平台），以"信誉担保而非资金担保"建立信任（区别于中介与交易平台），以"AI 兜底"解决冷启动稀疏（所有竞品都没有）。

一句话：**闲鱼的"求购"逻辑 + 小红书的社区语境 + 旅行的时效性，跑在微信里。**

## 3. 用户与场景

### 3.1 三类角色

角色**不是注册时的固定身份，而是可切换的行为状态**。同一个留学生今天是响应者（帮旅行者带路），下个月去别的城市旅行时就是需求方。这一点在 V1.0 中被写死成了"供给端/需求端"两类用户，2.0 改为单一账号 + 双向能力。

1. **需求方（喊人的）**：主体是短期到访欧美的中国旅行者，也包含当地留学生（找搭子、找二手、应急）。特征是需求具体、时效强、停留期短、决策快、信任基础薄。
2. **本地响应者（接活的）**：当地常驻华人、留学生、长期旅居者。特征是有在地信息与碎片时间，动机是赚钱、攒信用、社交，但**耐心有限**——被无效需求打扰两三次就会永久关闭通知。
3. **泛参与者**：其他旅行者、游客、短期访客。既可能顺手回答一句，也可能与需求方互为搭子。

**设计含义**：产品对两侧的容忍度不对称。需求方的门槛必须极低（低到一句话就能发出需求），响应者的打扰必须被严格控制（频控、精准分发、可关闭）。V1.0 对两侧一视同仁，是隐藏的供给流失源。

### 3.2 用户画像

**画像一｜林悦，26 岁，需求方**
上海某互联网公司运营，年假 10 天独自游伦敦+爱丁堡。会用小红书做攻略但不敢私信陌生人。痛点：想去大英博物馆但一个人逛没意思、不知道哪家中餐馆不坑、行李箱轮子坏了不知道去哪修、想拍几张出片的照片但不会自拍。她不缺钱，缺的是"当地有个人能问一句"。**决策逻辑：只要看起来靠谱、代价不高，就愿意试。**

**画像二｜陈默，23 岁，本地响应者**
UCL 研一，伦敦第二年，生活费紧张。会拍照、熟悉伦敦交通、有闲的周末。痛点：想赚点零花钱但正规兼职受签证工时限制、发在校友群的接单信息很快被淹没、遇到过临时放鸽子和压价。**决策逻辑：单子要值当（时间/收益比）、人要靠谱、流程别麻烦。**

**画像三｜苏姐，38 岁，长期旅居者/泛供给**
巴黎定居八年，做代购和自媒体。她是社区里的"信息节点"，愿意回答问题以积累影响力，也接高价值订单（陪同购物、翻译）。**决策逻辑：图长期 IP 与客源沉淀，不图单次收入。** 她是城市小组组长的最佳人选。

### 3.3 核心场景

按**时效类型**分两类，这是 2.0 新增的关键区分维度（V1.0 无此概念）：

**预约型（有明确未来日期，可提前规划）**

- S1 行前一周：林悦发"9/12 上午想找人一起逛大英博物馆，中文，女生优先" → 陈默的同学接单 → 双方私信约地点 → 完成 → 互评。
- S2 行前三天：找付费地陪一日游，含拍照，预算 £80 → 3 人响应 → 看信用分与作品选一个 → 生成约定单（线下现金/转账支付）。
- S3 行前：找短期住宿/行李寄存/借转换插头。

**即时型（当天或数小时内，需要主动分发与推送）**

- S4 落地当天："现在在国王十字，谁知道附近哪里能买到电话卡？" → 小螺解析并广播到伦敦小组 + 精准推给 5 位标注"熟悉本地生活"的响应者 → 若 30 分钟无人应答，小螺直接用社区历史内容作答兜底。
- S5 突发：护照丢了、生病、被警察拦下语言不通 → 应急求助卡（当地语言 + 步骤 + 使领馆信息）+ 同城响应者优先推送。
- S6 临时：今晚想拼饭/拼车去希思罗。

**平台侧场景**

- S7 陈默上线：选择伦敦、勾选可提供的能力标签（带路、拍照、翻译、代购、闲置转让）、验证 .edu 邮箱 → 进入城市响应池 → 收到匹配的需求卡片。

### 3.4 需求优先级

**P0（2.0 必须做，构成主干闭环）**：需求单发布（含 AI 解析）、需求单状态机、响应与选定、双向评价、城市社区与响应池、四层信任体系基础版、安全体系（拉黑/举报/紧急联系人/仅同性响应）、分级审核、小螺 Agent 的 L0/L1 档、消息通知。

**P1（2.0 做，体验杠杆高）**：小螺 L2 自动分发、AI 行程与落地清单、小红书图文生成、应急求助卡、内容→需求单一键转化、需求单二次投放、会员体系、信用分展示、城市小组健康度。

**P2（3.0 及以后）**：本地商家入驻位、长期搭子预约、跨城联动、多语言界面、约定单争议仲裁流程化、供给端认证徽章年费、担保交易（需主体与牌照条件成熟）。

## 4. 核心机制设计

### 4.1 需求单（Request）：产品的原子单位

V1.0 的原子是"帖子"，帖子只有内容，无法被"接"、无法闭环、无法度量。2.0 的原子是**需求单**：一个有明确诉求、明确时效、可被接受、可被完成、可被评价的对象。所有内容型帖子降级为社区内容，服务于供给端入驻与 AI 知识库。

**字段定义**

| 字段 | 必填 | 说明 |
|---|---|---|
| 品类 category | 是 | 搭子同行 / 付费地陪 / 借物易物 / 住宿 / 打听咨询 / 代购跑腿 / 翻译陪同 / 应急求助（8 类白名单，见 4.6） |
| 城市 city | 是 | 绑定城市社区，决定分发范围 |
| 标题 title | 是 | ≤20 字，可由 AI 生成 |
| 详情 detail | 是 | 自由文本 + 图片 ≤9 张 |
| 时效类型 timing | 是 | 预约型（含起止时间）/ 即时型（含有效时长：1h/3h/今天内） |
| 期望时间 expect_time | 预约型必填 | 日期 + 时段 |
| 地点/范围 area | 否 | 模糊到街区级，**不精确到门牌**（安全设计） |
| 报酬类型 reward_type | 是 | 免费互助 / 请一顿 / 付费（金额区间） / 以物换物 |
| 参考金额 amount | 付费时必填 | 仅作为**线下协商的参考区间**，平台不代收（见第 9 章） |
| 人数 headcount | 搭子类必填 | 1~N |
| 偏好 preference | 否 | 语言、仅同性响应（安全开关）、是否需认证响应者 |
| 可见范围 visibility | 是 | 城市社区公开 / 指定小组 / 仅定向邀请 |

**状态机**

```
草稿 Draft
  └─发布→ 招募中 Open ──有人响应→ 待选定 Responded
                                    ├─选定→ 已确定 Matched
                                    │         ├─双方确认→ 已完成 Done →互评→ 已评价 Rated
                                    │         └─任一方取消→ 已取消 Cancelled（记录取消方，计入信用）
                                    └─超时无选定→ 自动过期 Expired
  └─有效期到/超时无响应→ 已过期 Expired ──→（AI 兜底作答 / 归档进社区知识库）
  └─违规→ 已下架 Removed
```

**关键规则**

1. **需求单必然会终结**，不存在永久挂着的需求。预约型在期望时间后 24h 自动过期，即时型按有效时长过期。这直接解决 V1.0 的"死水内容堆积"。
2. **过期不等于浪费**：过期需求单连同其响应内容进入城市知识库，成为小螺 RAG 的语料。稀疏期的失败也在积累资产。
3. **取消要留痕**：谁取消、第几次取消都计入信用分。这是不碰资金下唯一的履约约束手段。
4. **同一用户同城同时在架需求单上限**：免费用户 3 条，会员 10 条。防刷屏。

### 4.2 撮合流程

```
需求方                        平台/小螺                      本地响应者
  │                              │                              │
  ├─ 一句话说出诉求 ────────────▶ AI 解析成结构化需求单           │
  │  ◀── 预填表单，用户确认/修改 ─┤                              │
  ├─ 发布 ──────────────────────▶ 机审（毫秒级）                 │
  │                              ├─ 命中风险→转人工，否则直接可见 │
  │                              ├─ 分发决策：                   │
  │                              │   ① 城市社区信息流展示         │
  │                              │   ② 精准推送匹配响应者（订阅消息）─▶ 收到需求卡片
  │                              │   ③ 广播到相关小组             │
  │                              │                              ├─ 响应（附一句话+报价）
  │  ◀── 响应列表（含信用档案）───┤◀─────────────────────────────┤
  ├─ 选定 1 位 ─────────────────▶ 生成约定单，开启 1v1 私信 ─────▶ 收到选定通知
  │                              │                              │
  ├─────────── 线下完成，双方各自点击"已完成" ──────────────────┤
  │                              ├─ 双向评价（互评前互不可见）    │
  │                              └─ 更新信用分 / 沉淀城市知识库   │
  │                              │                              │
  │              ※ 2 小时无响应 → 小螺二次改写投放（≤2 次）       │
  │              ※ 仍无响应 → 小螺基于城市知识库直接作答兜底       │
```

**约定单（Agreement）**：选定后自动生成的一张只读卡片，字段为「谁、什么时间、在哪、做什么、约定报酬多少、线下如何支付」，双方均可见、不可单方修改（修改需双方重新确认，留版本记录）。它替代了 V1.0 的"担保交易"——**平台托管的是共识与凭证，不是钱**。发生纠纷时，约定单 + 聊天记录 + 评价构成判定依据，处理结果体现为信用分与封禁，而非退款。

### 4.3 城市社区：供给的容器

设计原则：**城市是唯一的一级容器，小组是城市下的二级分区。** V1.0 中首页与"组圈"职责重叠、用户可无限自建小组，导致流量碎片化。2.0 收拢为：

- 城市（官方维护，全球开放浏览，运营重点城市为伦敦）
  - 官方分区（每城固定 5 个，与需求单品类对齐）：找搭子、问本地、跑腿代购、闲置转让、住宿
  - 兴趣小组（用户可申请创建，受**健康度约束**）

**小组健康度机制（替代 V1.0 的"7 天无互动降权"）**

每个小组每周计算健康分，输入为：周活跃发帖人数、需求单产生数、首响率、成员留存。

- 健康分 ≥60：正常展示
- 30~60：降权，不进推荐位，提示组长发起话题（小螺可代写话题）
- <30 连续 3 周：进入"沉寂"状态，停止新成员进入、内容合并到城市官方分区、小组归档
- 新建限制：一个城市同时活跃的兴趣小组上限 = 该城市周活跃用户数 / 20，向下取整（伦敦初期即 0~2 个）。**这条是有意的克制**：冷启动期把流量按住在官方分区，不允许提前碎片化。

**开城标准（伦敦跑通后才复制下一城）**

同时满足：认证本地响应者 ≥50 人、周需求单 ≥30 条、需求单首响率 ≥60%、本地响应者次月留存 ≥40%。未达标不开新城，全部运营资源留在伦敦。理由：撮合是密度游戏，个人开发者的运营带宽只够一座城；3 城试点等于把密度除以 3。

**冷启动渠道用学校，产品结构用城市。** 旅行者只知道城市不知道学校，所以容器必须是城市；但留学生群体天然按学校组织（学生会、新生群、二手群、校友会），所以 BD 动作按学校推进（伦敦首批：UCL、KCL、IC、LSE）。这两件事不矛盾，V1.0 的困惑源于把渠道和结构混为一谈。

### 4.4 信任体系：四层信任，不收证件

**核心设计取舍**：既要用户尽可能低门槛入驻，又要有安全保证。解法不是把认证做强，而是**放弃"已认证/未认证"的二元标签，改为"信任分档 + 证据清单"，并把强制校验推迟到高风险动作发生的那一刻**。注册时零门槛，接付费单时才要求补齐。

**为什么不收证件**：护照、签证、学生证属于身份证件类敏感个人信息。在 GDPR 下处理这类数据需要明确的合法性基础、数据保护影响评估、加密存储与最小化留存；个人开发者不具备承担这一合规责任的能力，一次泄露的后果远大于产品收益。因此 2.0 **完全不采集证件影像**。

**四层信任（可累加，逐层增信）**

| 层 | 名称 | 获取方式 | 是否需要资质 | 可信度 |
|---|---|---|---|---|
| L1 | 基础身份 | 微信授权登录（头像昵称）+ 常驻城市自选 + 性别自填（可留空） | 无 | 低 |
| L2 | 自证 | ① `.edu`/学校邮箱验证码（仅存"已验证 + 学校名"，不存邮件内容）② 社媒绑定 ③ 自我介绍完整度 | 无 | 中 |
| L3 | 履约 | 真实完成的需求单数、双向评价、平均响应时长、被举报率、取消率 | 无 | **高** |
| L4 | 社区背书 | 城市组长/老用户为新用户背书（每人每月限 2 次，被背书者违规则背书人连带扣分） | 无 | 高 |

**为什么 L1 不采集手机号**：微信的手机号快速验证接口对个人主体小程序不开放（按"不可用"处理，待核实项记在 `progress.md`），自建短信验证要买通道且面向海外号码成本与合规都不划算。改为纯微信授权登录——云函数拿到的 openid 本身就是微信校验过的可信身份（`tech-stack.md` 第 2 节），手机号在本产品里并不额外提供可信度，去掉它同时符合 9.4 的数据最小化。

**性别字段的用途只有一个**：支撑 4.5 的「仅同性响应」安全开关。自填、可留空、不做校验；**未填写性别的用户不能响应设了该开关的需求单**（提示补全即可解锁），这样开关才有服务端可校验的依据，而不是只在前端提示。除此之外性别不参与任何排序、推荐或筛选（D-09：不提供任何异性偏好选项）。

**社媒绑定的零资质实现方案**（这是"链接小红书增强可信度"的可落地做法）：用户提交小红书/Instagram 个人主页链接，平台生成一串一次性口令，要求用户临时把口令加进个人简介，平台校验后**只存储"已绑定 + 主页 URL + 校验时间"**，不抓取、不存储对方平台内容。零成本、零资质、可信度提升明显，且用户随时可解绑。

**喊呗信任分（0~100）**

- 构成：L1 基础 10 分 + L2 自证最高 20 分 + L3 履约最高 60 分 + L4 背书最高 10 分
- 展示形态：**不显示裸分数**，显示为四档徽章（新面孔 / 靠谱 / 老手 / 城市之光）+ 可展开的证据清单（"已完成 12 单｜好评率 100%｜平均 18 分钟响应｜UCL 邮箱已验证"）
- 关键原则：**让用户看到"他凭什么可信"，而不是一个不可解释的分数**。分数不可解释会同时打击被评者的积极性和求助者的信心。

**强制校验点（只在这三处拦截，其余全程不拦）**

1. 接"付费地陪 / 翻译陪同"类需求单 → 需 L2 完成 + 信任分 ≥40
2. 发布或接"住宿"类需求单 → 需 L2 完成 + 至少 1 条历史好评
3. 首次发起 1v1 线下见面确认 → 强制阅读安全提示并勾选

**降低警惕心理的产品手法**：补全资料的引导不用"为了安全请认证"（暗示危险），而用"补全后被选中的概率高 2.6 倍"（收益框架），并在响应列表中让高信任分用户天然排序靠前——让增信的动机来自竞争而非恐惧。

### 4.5 安全体系（P0）

这是一个促成陌生人在异国线下见面的产品，安全模块是核心差异化而非附加项，因此定为 P0 并写入产品定位。

**事前**

- **仅同性响应开关**：需求方可设置本单仅同性可响应（默认关闭，女性用户首次发单时主动提示）。依据是双方在个人资料里自填的性别（4.4）；未填性别的用户不能响应设了该开关的需求单，提示补全后解锁
- **地点模糊化**：需求单地点只精确到街区/地铁站级，不允许填写住址门牌；系统对疑似详细地址做提示拦截
- **安全提示卡**：选定响应者后强制展示一次，内容为"首次见面选公共场所、不提前转账、不交出证件、告知朋友行程"
- **住宿类特殊规则**：住宿品类默认要求双方均 L2 完成，且强制展示独立的住宿安全须知

**事中**

- **行程报备**：一键生成行程卡片（对方昵称+信任档位+时间+街区+约定内容），通过微信分享给指定联系人或群。**不做后台存储的"紧急联系人"字段**，避免采集第三方个人信息——用微信自带的分享能力即可达到同等效果，这是零成本、零合规负担的解法
- **一键 SOS**：在进行中的需求单页面常驻，点击后弹出当地紧急号码（按城市配置：英国 999、欧盟 112、美国 911）+ 中国使领馆电话 + 一键把当前行程卡片发送给此前报备的联系人
- **反诈风险提示（AI）**：私信中出现"先转账""押金""发身份证照片""加我微信私下聊""退出平台交易"等模式时，向双方弹出风险提示。提示对话双方而非只提示一方，避免误伤正常沟通

**事后**

- **双向评价**：互评前互不可见，7 天内未评视为默认好评但不计入好评率
- **拉黑**：拉黑后互相不可见需求单、不可响应、不可私信
- **举报**：分类明确（人身安全 / 擦边交友 / 诈骗 / 引流 / 违规内容 / 未履约），人身安全类举报进入最高优先级队列并直接冻结被举报人接单能力
- **处罚阶梯**：提示 → 限流（需求单不进推荐）→ 禁止接单 7 天 → 永久封禁（设备+微信 openid 维度）

### 4.6 内容治理与分级审核

**分级审核（替代 V1.0 的先审后发）**

| 用户/内容分级 | 策略 |
|---|---|
| 新用户前 3 条内容、或信任分 <30 | 机审 + 人工复核后可见（目标 30 分钟内） |
| 信任分 ≥30 且无违规记录 | 机审通过即可见，先发后审 |
| 敏感品类（住宿、应急求助、含金额的付费单） | 一律机审 + 人工抽检 |
| 命中高风险语义 | 直接拦截，不可发布，给出可修改提示 |

机审由 AI 承担（见 5.2 能力 #8），毫秒级；人工复核由个人开发者在简易后台处理，配合"待审队列 + 一键通过/驳回模板"，目标每日处理时间 <20 分钟。

**反擦边交友治理（对应 1.4 明确不做）**

1. **品类白名单**：只有 8 个品类，没有"交友""同城""聊天"选项。无法归入 8 类的需求无法发布。
2. **语义识别拦截**：拦截"仅限异性""看颜值""长期关系""包吃包住陪玩""有偿陪伴"等表述及其变体、谐音、拼音缩写。
3. **偏好字段单向可用**：性别偏好只能用于"仅同性响应"（安全用途），**不提供"仅异性响应"选项**——这是从数据结构层面消灭擦边需求。
4. **举报独立分类**："擦边交友"作为一级举报类型，处理优先级仅次于人身安全。
5. **处罚从重**：擦边交友类违规跳过提示，直接禁止接单 7 天，二次永久封禁。

治理原则写进社区规范首屏：**喊呗解决的是"办事"，不是"处对象"。** 让规则以产品价值观的方式表达，比藏在协议里有效。

### 4.7 反死水机制汇总

V1.0 只有三条规则，2.0 从五个层面同时施压：

1. **需求层**：需求单强制有时效并自动过期，社区里永远只陈列"还有效的事"（4.1）
2. **分发层**：不依赖用户主动刷，靠精准推送 + 小组广播 + 二次改写投放把需求送到人面前（4.2、5.3）
3. **容器层**：小组健康度 + 建组数量上限，冷启动期强制流量收拢（4.3）
4. **兜底层**：无人响应时 AI 直接作答，把"发了没人理"的流失挽回（5.1）
5. **运营层**：每日城市话题机器人、每周精华摘要、组长激励、学校 BD（第 11 章）

配套的**内容播种**：伦敦上线前，把常见问题（换电话卡、机场交通、退税、看病、报警、便宜超市、中餐推荐）预先做成 30 条高质量社区内容 + 100 条问答语料，同时作为小螺的初始知识库。**冷启动期的"社区"可以是人工的，但不能是空的。**

## 5. AI 能力设计

### 5.1 AI 战略定位

一句话：**在喊呗里，AI 不是效率工具，AI 是供给的兜底层。**

推导过程：本产品最致命的流失点不是"匹配不精准"，而是"发了需求没人理，用户当天就走了"——而旅行者在当地只停留几天，这类流失不可挽回。冷启动期供给必然稀疏，这不是运营能在短期解决的问题。因此 AI 的第一价值不是提效，而是**在真人供给缺席时，先把这个用户的需求兜住**，用城市社区的历史内容做 RAG 给出一个可用答案。

由此得到三条 AI 产品原则：

1. **AI 是供给的兜底层，不是替代层**。真人响应永远优先展示，AI 答案只在无响应或用户主动询问时出现，且明确标注来源。
2. **AI 承担"从模糊到结构化"的翻译工作**。用户不需要学会填表，这是需求方门槛降到最低的唯一办法。
3. **AI 的自主性由用户选择，而非由产品单方决定**。见 5.3。

**数据飞轮**（这是本产品 AI 侧最重要的长期资产）：

```
社区内容 + 历史需求单 + 真人回答
        ↓ 按城市分片入库（起步：关键词 + 标签检索；达到升级条件后再向量化）
   小螺 RAG 质量提升
        ↓
兜底答案更有用 → 用户留存 → 更多需求单与回答
        ↓
   语料继续增长（回到起点）
```

关键含义：**喊呗的 AI 护城河不在模型，在城市语料**。同一个模型，有伦敦三年问答语料的产品和没有的产品，输出质量完全不同。这也解释了为什么必须单城做深——语料密度和撮合密度是同一件事。

### 5.2 「小螺」Agent 能力地图

形态：**底层能力 + 一个对话式助手入口双轨**。底层能力隐形嵌在发布、匹配、审核链路里（用户感知不到 AI，只感知到"变简单了"）；对话入口承载复杂意图与兜底问答。

Agent 工具集（function calling）：

| # | 工具 / 能力 | 触发位置 | 优先级 |
|---|---|---|---|
| 1 | `parseRequest` 一句话→结构化需求单 | 发布页顶部输入框、助手对话 | P0 |
| 2 | `createRequest` 确认后创建需求单 | 助手对话 | P0 |
| 3 | `searchKnowledge` 城市语料 RAG 检索 | 兜底作答、助手问答 | P0 |
| 4 | `matchResponders` 匹配响应者 + 生成推荐理由 | 需求单发布后 | P1 |
| 5 | `draftInvite` 生成定向邀请文案 | L1 一键代发 | P1 |
| 6 | `broadcast` 分发到城市/小组 + 二次改写投放 | L2 自动分发 | P1 |
| 7 | `generateChecklist` 落地清单 / 行程建议 | 助手对话、需求单详情 | P1 |
| 8 | `moderate` 内容风险分级 | 所有 UGC 提交时 | P0 |
| 9 | `riskHint` 私信反诈提示 | 私信会话 | P0 |
| 10 | `generateXhsPost` 小红书图文生成 | 完成需求单后、我的-作品 | P1 |
| 11 | `emergencyCard` 应急求助卡（当地语言） | SOS、应急求助品类 | P1 |
| 12 | `dailyTopic` 城市话题 / 周精华摘要 | 定时任务 | P1 |
| 13 | `summarizeReviews` 评价聚合成信任标签 | 个人主页 | P2 |
| 14 | `translate` 短文本翻译与破冰话术 | 私信 | P2 |

**关于 #10 的诚实定义**：功能命名为「生成小红书图文」而**不是**"同步到小红书"。产品行为是：生成封面图（模板套图，非 AI 绘图）+ 正文文案 + 话题标签 → 一键复制文案 + 批量保存图片到相册 → 提示用户手动打开小红书发布。小红书没有开放给第三方的发布接口，任何声称"一键同步"的产品实质都是这套流程。**在 PRD 里把技术不可行的地方写清楚，比留一个做不出来的需求更负责。**

**关于 #11 应急求助卡**：按城市预置结构化模板（丢护照/生病/被盗/交通事故/语言不通），输出内容 = 处置步骤 + 当地语言短句（可直接给对方看的大字卡片）+ 使领馆与紧急号码。事实性内容来自预置结构化数据而非模型自由生成，模型只负责组织与翻译——**高风险场景不让模型编事实**。

### 5.3 自主性阶梯：把"该不该自动"变成用户可选的产品维度

这是本产品 AI 设计的核心主张。全自动有风险、纯手动没价值，正确答案不是在两者之间取一个折中点，而是**把自主性本身产品化为一个可解释、可调节、可回退的档位**，默认值保守，由用户按信任程度自行上调。

| 档位 | 名称 | Agent 可做 | Agent 不可做 | 默认对象 |
|---|---|---|---|---|
| **L0** | 只读建议 | 解析需求、给攻略与清单、答疑 | 不对外发送任何内容 | 新用户前 3 单 |
| **L1** | 一键代发 | 生成邀请文案 + 候选人名单，等你勾选后统一发出 | 不自动发送 | **全局默认档** |
| **L2** | 自动分发 | 需求单发布后自动向匹配响应者推送**结构化需求卡片**；2 小时无响应自动改写文案二次投放（≤2 次） | 不进入 1v1 私信、不模拟真人语气、不代答追问 | 用户手动开启 |
| **L3** | 自动协商 | —— | **本产品不做**（理由见下） | 不提供 |

**L2 的形态约束很关键**：Agent 对外触达只能是"系统需求卡片"，视觉上明确是卡片而非聊天气泡，并强制带「由小螺代为分发」标识。这样既拿到了自动分发的效率，又不产生"AI 冒充真人"的问题。

**为什么不做 L3（自动协商）**——写入 Roadmap 的"明确不做"，并给出理由：

1. **责任无法归属**。AI 谈定的见面时间地点若发生人身安全事件，责任链条不清。
2. **AI 承诺会造成真实损失**。谈价、谈时间属于对现实世界的承诺，模型出错的代价由用户承担。
3. **伦理与合规**。AI 以真人语气与人协商却不明示身份，在多数地区已属需要披露的行为。
4. **能力边界诚实**。个人开发者无力承担由此产生的纠纷处理与客服成本。

**L1 → L2 的引导设计**：不在设置页里藏一个开关等用户发现，而是在"L1 发送邀请后获得响应"这个正反馈时刻提示："下次要不要让小螺自动帮你喊人？"——在信任已建立的时刻请求更多授权，这是自主性上调的正确时机。

### 5.4 护栏与红线

| 类别 | 规则 |
|---|---|
| 身份明示 | Agent 产出的一切对外内容强制带「AI 协助」标识，助手对话首屏声明"我是 AI" |
| 四类字段禁止代填 | 金额、见面时间、见面地点、联系方式——Agent 只能留空，必须由人填写 |
| 频控 | 同一响应者每日被 Agent 触达 ≤3 次；被静默或拒绝 2 次后进入 7 天冷却 |
| 事实性边界 | 签证、医疗、法律、移民问题直接拒答，给出官方链接与"请咨询专业机构" |
| 来源标注 | 兜底答案必须标注来源（"根据伦敦小组 3 条历史回答，请自行核实"） |
| 追问上限 | 解析失败最多追问 2 轮，之后降级为普通表单，禁止死循环 |
| 可解释性 | 每条推荐必须给出依据字段（城市匹配 / 能力标签 / 完成单数 / 响应速度），不允许"猜你喜欢"式无理由推荐 |
| 可回退 | 任何 AI 生成内容均可一键改为手动编辑；L2 可随时关闭且立即生效 |

### 5.5 AI 评测指标

AI 功能必须可度量，否则无法判断该不该继续投入。每项能力绑定一个可观测指标与达标线：

| 能力 | 指标 | 达标线 |
|---|---|---|
| 需求单解析 | 字段抽取准确率 | ≥85% |
| 需求单解析 | 用户提交前的字段修改率 | ≤30% |
| 需求单解析 | 发布转化率提升（vs 纯表单，A/B） | +20% |
| 智能分发（L2） | 需求单首响率（vs 纯社区展示，A/B） | +30% |
| 智能分发 | 响应者被打扰投诉率 | ≤2% |
| 兜底作答 | 采纳率（用户点"有用"或未继续追问） | ≥50% |
| 兜底作答 | 无响应需求单的当日留存挽回率 | ≥25% |
| 机审 | 违规漏放率 / 正常内容误杀率 | ≤3% / ≤5% |
| 小红书图文 | 生成后实际复制/存图率 | ≥40% |
| 全局 | 每次成功撮合的 AI token 成本 | ≤0.10 元 |

**分阶段验证（2026-08-29 调整，见 D-31）**：上表中带「vs / A/B」的三项（发布转化率 +20%、首响率 +30%、投诉率）依赖真实流量，**在有真实用户之前无法验证，推后到 M5**。M2 阶段改用**离线评测集**证明 AI 质量：自建 30~50 条真实语料的黄金标注（人工标出正确的品类、时效、报酬类型等字段），跑一次评测脚本得到字段抽取准确率，这一项不需要任何用户即可度量，也是对外展示 AI 能力时最实在的材料。分桶能力仍在 M1 就把字段埋进每条事件（保证将来有用户时历史数据不缺失，D-21），但实验配置与对比分析等到 M5 再做。

### 5.6 AI 成本模型与付费设计

**成本估算**（按国产便宜模型档位，DeepSeek / 豆包 / Qwen-Turbo 级）：

| 能力 | 单次 token 量级 | 单次成本（人民币） |
|---|---|---|
| 需求单解析 | 输入 1~2k / 输出 ~300 | 0.001~0.005 |
| 机审 | 输入 <1k / 输出 极短 | <0.001 |
| RAG 兜底作答 | 输入 3~5k / 输出 ~500 | 0.005~0.02 |
| 落地清单 / 行程生成 | 输入 2k / 输出 5~8k | 0.02~0.05 |
| 小红书文案 | 输入 1k / 输出 1~2k | 0.005~0.015 |

结论：**短文本能力完全给得起免费**。日活 500、人均 3 次短文本调用的规模下，AI 月成本在几十元量级，个人开发者可承担。真正贵的是长输出和图像生成——因此小红书图文只做模板套图不做 AI 绘图，行程生成设每日限额。

**额度设计**

- **无限免费**：需求单解析、内容转需求单、机审、反诈提示、短文本翻译与破冰、评价标签聚合
- **每日限免（免费用户）**：AI 行程与落地清单 1 次/天、小红书图文 1 次/天、L2 自动分发 1 单/天、兜底追问 5 轮/天
- **会员放开**：上述额度 ×10 或不限

**定价原则（重要）：不给"AI 调用次数"定价，给"结果"定价。** 会员权益的对外表述是"更快被人响应、更容易被选中"，AI 额度只是实现手段，不作为卖点陈列。一旦让用户按次数计算 AI 成本，付费意愿会立刻崩塌，而且会把产品价值锚定在"AI 工具"而非"撮合服务"上。

### 6.1 五 Tab 重定义

V1.0 的 Tab 命名不统一（导图为"定位"、高保真图为"组圈/组队"），且首页与组圈职责重叠。2.0 明确分工：

### 6.3 全局跳转逻辑

```
首页 → 需求卡片 → 需求单详情 → 响应 → 私信会话 → 约定单 → 完成 → 评价
首页 → 城市切换器 → 切换城市（首页与城市 Tab 联动同一城市态）
首页 → 悬浮球 → 小螺助手 → 对话产出需求单 → 确认 → 需求单详情
Tab2 城市 → 官方分区 → 帖子详情 → 「我也想问/我也要」→ 预填发布页
Tab2 城市 → 本地响应者名录 → 个人主页 → 定向邀请（需已有在架需求单）
Tab3 喊一声 → 一句话输入 → AI 解析 → 表单确认 → 发布 → 需求单详情
Tab4 消息 → 需求单通知 → 需求单详情｜互动通知 → 内容详情｜私信 → 会话
Tab5 我的 → 我的需求单 → 状态分组（招募中/待选定/进行中/已完成/已过期）
Tab5 我的 → 信任档案 → 增信任务清单（邮箱验证/社媒绑定/完善介绍）
```

### 6.4 关键页面交互要点

**发布页（最重要的转化页面）**

- 首屏只有一个输入框和一句提示："想找人做什么？一句话说清就行"。**不首屏展示表单**——表单是解析后的结果，不是输入的起点。
- 用户输入后点"帮我整理"，AI 解析出品类、时效、城市、报酬类型，以卡片形式展示"我理解成这样，对吗？"，每个字段可点击修改。
- 解析失败或用户跳过 AI → 降级为普通表单，不阻断。
- 金额、见面时间、见面地点三个字段即使 AI 有推测也留空高亮，提示"这几项请你自己确认"。
- 底部实时展示预期："发出后将推送给伦敦 23 位可能帮上你的人"——把不可见的分发过程可视化，这是提升发布意愿的关键。

**需求单详情页（响应者视角）**

- 顶部即为决策所需的全部信息：品类、时效倒计时、报酬、地点范围、需求方信任徽章。
- 响应按钮附带一句话输入与报价输入（付费类），降低响应成本到 10 秒内。
- 明确展示"已有 N 人响应"，避免响应者做无效投入。

**响应列表（需求方视角）**

- 每条响应展示：昵称、信任徽章、证据摘要（完成单数/好评率/平均响应时长）、报价、一句话自荐、AI 推荐理由。
- 排序默认按"信任分 + 响应速度"综合，可切换按报价。
- 选定为不可逆动作，二次确认并同时展示安全提示卡。

## 7. 数据与指标体系

### 7.1 指标框架

- **北极星指标**：每周成功撮合数（需求单被接 + 双方确认完成）
- **护栏指标 1**：需求单首响率（发布后 2 小时内获得至少 1 条响应的比例），目标 ≥60%
- **护栏指标 2**：本地响应者次月留存，目标 ≥40%

选择理由：撮合数直接代表产品创造的真实价值，且同时依赖供需两侧，无法靠单侧刷量做高。首响率是撮合数的领先指标，能在撮合完成前就暴露密度问题。响应者留存是供给侧的瓶颈指标——需求方是流动的（旅行者用完即走），供给方才是留存的根基，供给一旦流失，产品立刻回到死水状态。

**明确不作为核心指标**：DAU、发帖量、小组数量。V1.0 的数据看板以这三项为主，它们在本产品中都是可以靠"看内容"刷出来的虚荣指标，与撮合成功无因果关系。

### 7.2 核心漏斗

```
进入城市 → 浏览需求/内容 → 发起需求单 → 获得首响 → 选定 → 线下完成 → 双向评价 → 复用
                              ↓ 未发布              ↓ 无响应
                      发布转化率（AI 解析优化）   兜底作答挽回率
```

各环节目标：发布转化率 ≥25%（浏览到发布）、首响率 ≥60%、选定率 ≥80%（有响应的单最终选定）、完成率 ≥70%、评价率 ≥60%、30 天内二次发单率 ≥20%。

### 7.3 埋点要求

需求单全生命周期状态变更、AI 每次调用（能力类型/耗时/token/是否被采纳/是否被修改）、分发触达与响应归因（响应来自推送/社区/邀请/广播哪条路径）、增信任务完成漏斗、安全功能使用率（仅同性开关/行程报备/SOS）、A/B 分桶标识。

## 8. 商业化设计

### 8.1 前置结论：不碰资金

平台不代收、不代付、不托管任何用户资金，付费类需求的钱款由双方线下自行结算。这不是妥协，而是当前条件下的最优解，理由见 9.2。相应地，**平台把"担保"从资金担保替换为信誉担保**：托管约定单、沉淀双向评价、留存纠纷证据、以信用分和封禁作为约束手段。这套机制提供了担保交易约 80% 的信任价值，而风险与合规成本接近于零。

### 8.2 四阶段商业化路线

**阶段 0｜验证期（0~6 个月）：不赚钱**
唯一目标是把伦敦的每周成功撮合数跑起来。任何收费都会在密度不足时杀死冷启动。此阶段所有 AI 能力与功能全部免费。

**阶段 1｜会员订阅（撮合量稳定后）**
向**需求方**收费，卖的是"更快被响应、更容易被选中"：

- 需求单置顶/加急曝光
- 在架需求单上限从 3 提升到 10
- 查看响应者的完整信用档案与历史评价明细
- 高级筛选（语言、认证层级、同校、同城时长）
- AI 高成本能力额度放开（行程生成、小红书图文、L2 自动分发）
- 已读回执、优先客服

定价建议 ¥18/月 或 ¥88/年。**iOS 规避**：微信小程序内的虚拟权益在 iOS 端受平台规则限制，方案是 iOS 端不展示购买入口、仅展示权益说明并引导至安卓端或公众号 H5 完成购买，权益按账号生效跨端通用。这一点必须在开发前确认当期微信与 Apple 的最新规则。

**阶段 2｜供给端变现（更健康的收入）**
向**本地响应者**收费。供给端有真实收益动机，付费意愿显著高于旅行者：

- 认证徽章年费（含人工背景核验与主页展示位）
- 接单曝光包（在城市响应者名录与响应列表中获得优先展示）
- 个人服务主页（长期沉淀作品与评价，做本地向导 IP）

**阶段 3｜本地商家与生态（收入天花板最高，且完全不碰资金）**
当地华语商家的城市入驻位与内容推广位（中餐馆、民宿、旅行社、接送机、驾照代办、搬家），以及留学生活服务的 CPA 分成（eSIM/电话卡、境外保险、换汇、行李托运）。这是海外华人流量最成熟的变现方式，按曝光/线索计费，无资金归集。

**阶段 4｜担保交易（长期，条件成熟才做）**
需要企业主体、支付资质或持牌第三方合作、专职客服与风控。在个人开发者阶段**明确不做**，但产品的数据结构（约定单、金额字段、状态机）预留了升级空间。

### 8.3 单位经济与可持续性

个人开发者视角的成本结构：服务器与数据库（云函数 + 托管数据库，月 30~100 元）、AI token（日活 500 量级月几十元）、域名与备案（年百元级）、人工审核（自身时间，目标 <20 分钟/天）。结论：**月运营成本可控制在 200 元以内**，达到阶段 1 后单城即可覆盖成本。这个数字本身就是"不碰资金 + 用便宜模型 + 单城做深"三个决策的合理性验证。

## 9. 合规与落地路线（最高优先级风险）

### 9.1 核心风险：个人主体无法上线 UGC 社区类小程序

**这是本项目最大的落地障碍，优先级高于任何功能设计。**

已核实的规则要点（截至 2026 年 8 月的公开信息，**开发前必须以微信公众平台官方文档再次确认**）：

- 微信小程序中涉及用户发帖、评论、动态、私聊、关注等 UGC 与社交功能，需要「社交-社区/论坛」或「社交-笔记」类目。
- 这些类目**不向个人主体开放**，后台入口为灰态，无法提交审核。个人主体小程序实质上只能做无用户互通的工具与信息展示类产品。
- 开通路径为：注册企业或个体工商户主体 → 完成 ICP 备案 → 申请对应类目。非经营性内容可免 ICP 经营许可证，涉及广告或会员收益则需要经营许可证（个人与个体户通常无法办理）。
- 社交、文娱类小程序通常会进入网信部门二次审核，周期一周至一个月不等。

**主体成本参考（区间估算，以实际所在地为准）**

- 个体工商户：注册基本免费或数百元，记账要求低，可自行零申报，年综合成本约 500~1500 元
- 有限公司：注册资本认缴制无需实缴；自办流程 + 刻章约数百元；地址挂靠 800~2000 元/年；代理记账 200~500 元/月。首年综合成本约 3000~8000 元
- 商标注册（个人可申请）：官费约 300 元/类

在"业余时间、投入资金近 0"的约束下，**不建议现在注册主体**。

### 9.2 为什么不碰资金（补充说明）

即使注册了主体，代收代付也不可行：微信支付的跨境结算与境外商户能力需要企业资质与外汇备案；向海外个人账户打款属于持牌的支付/汇款业务；一旦形成预付资金池，将涉及无证经营支付业务的法律风险，且退款纠纷会吞掉个人开发者的全部时间。因此"不碰资金"是长期结论，不是阶段性妥协。

### 9.3 落地路线：A + B 双 Demo

结合"产品要真实可用"与"作为求职作品集"两个目标，采用双 Demo 并行：

**Demo A｜可真实使用的完整版（主线）**

- 完整前端 + 后端 + 数据库，P0 功能全部真实可用，AI 能力接真实模型
- 发布形态：**微信小程序体验版**。体验版无需提交审核即可分享给受邀体验成员使用，因此不受个人主体类目限制。这是零成本、零合规风险、且能获得真实用户数据的唯一路径
- 体验成员数量有上限（以微信当期规则为准，需在开发前确认），因此天然适配"伦敦单城 + 小范围真实运营"的冷启动策略
- 面试展示方式：真机演示 + 后台数据看板 + AI 效果数据

**Demo B｜升级路径演示版**

- 用于演示"如果具备主体与资质，产品会长成什么样"：担保交易流程、本地商家入驻、供给端认证徽章、多城市联动、跨城数据看板
- 形态为高保真交互原型（不接后端），标注为"Roadmap 演示"，与 Demo A 明确区分
- 价值在于展示产品的完整商业推演能力，同时诚实标注当前不可落地的原因

**升级触发条件**：伦敦达到 8.2 阶段 1 的收入验证（或有明确融资/合作意图）时，再启动主体注册 → ICP 备案 → 类目申请 → 正式发布。届时 Demo A 的代码与数据可直接迁移。

### 9.4 其他合规事项

- **GDPR**：用户主要位于欧盟/英国。需提供独立可访问的隐私政策与用户协议、明确数据用途与保留期、提供账号与数据删除入口。**不采集证件影像、不采集精确位置、不采集第三方联系人信息**（4.4、4.5 的设计已规避主要风险点）。
- **数据最小化**：位置只到城市与街区级；社媒绑定只存 URL 与校验结论；邮箱验证只存"已验证 + 学校名"。
- **UGC 基础四件套**（无论何种发布形态都必须具备）：内容风控与关键词/语义拦截、举报与拉黑入口、独立的隐私政策与用户协议页、明确的社区规范。
- **未成年人**：注册要求 18 岁以上，需求单中涉及未成年人陪同的直接拦截。

## 10. 技术实现约束

面向"个人开发者、业余时间、成本近 0"的现实约束，技术选择服从两个原则：**能力够用即可，且不引入需要持续付费或运维的组件。**

| 环节 | 方案 | 说明 |
|---|---|---|
| 前端 | 微信小程序原生 | 明确不用 Taro / uni-app：只有一个交付端，跨端能力用不上（tech-stack 第 13 节） |
| 后端与数据库 | 微信云开发（云函数 + 云数据库 + 云存储） | 免服务器运维、有免费额度、与小程序鉴权天然打通 |
| 1v1 私信 | 云数据库轮询 + 云开发实时数据推送 | **不自建 WebSocket 长连接**，避免运维成本；消息实时性要求可放宽到秒级 |
| 消息触达 | 微信订阅消息（一次性订阅） | 免费。**关键约束：一次授权对应一条推送**，因此每次发布需求单/收到响应时都要顺势请求授权，这是产品设计必须配合的技术限制 |
| AI 调用 | 云函数代理调用国产模型 API | 密钥不落前端；统一做频控、额度、缓存、成本统计 |
| RAG | 城市语料按城市分片检索；**起步用关键词 + 标签过滤，暂不上向量库** | 冷启动期语料只有几百条，向量检索的质量提升观察不到，却多一个必须维护同步的组件。升级触发条件：单城语料 >2000 条，或兜底采纳率 <50%（5.5）。语料来源见 11.1 与 4.1 规则 2 |
| 图片 | 云存储 + 小程序端压缩 | 上传前压缩，控制存储成本 |
| 运营后台 | **小程序内的管理员页面**（openid 白名单 + 云函数二次校验管理员身份） | 只做待审队列、举报队列、用户管理、数据看板四件事；不做独立 Web 后台，理由见 D-22。四件事均属 M3，其中数据看板若排期紧可暂缓（先看云开发控制台） |
| A/B 与埋点 | 云函数配置表 + 自建埋点集合 | 满足 5.5 的评测需求即可，不引入第三方分析 SDK |

**明确的技术不可行项（写入文档避免后续返工）**

1. 小红书内容同步：无开放发布 API，只能生成内容 + 复制 + 引导手动发布（5.2）
2. 小程序无法直接跳转外部 App：无法一键打开小红书，只能复制到剪贴板并提示用户手动打开
3. 主动推送：不存在无授权的主动推送能力，只能依赖订阅消息，因此 L2 自动分发的触达率上限受用户授权率约束
4. 精准定位：境外定位精度与授权率均低于国内，因此城市采用"自动定位 + 手动选择"双轨，且所有逻辑以手动选择为准

## 11. 运营与冷启动

### 11.1 伦敦冷启动三步

**第 0 步：上线前把社区填满（不能空着）**

- 预置 30 条高质量社区内容：换电话卡、机场交通、退税、看病流程、报警与紧急号码、便宜超市、中餐推荐、地铁卡、租房避坑、常见诈骗
- 预置 100 条问答语料作为小螺的初始知识库
- 预置 5 个官方分区与规范首屏

**第 1 步：先攒供给（学校为抓手）**

- 目标：50 位认证本地响应者
- 渠道：UCL / KCL / IC / LSE 的学生会、新生群、二手群、校友会；小红书上活跃的伦敦留学生博主
- 话术切入点是收入与轻松感，不是"来做志愿者"："周末带人逛一天，赚顿饭钱 + 攒信用"
- 冷启动激励（零成本）：首批 50 人授予"创始响应者"永久徽章 + 城市响应者名录永久优先展示位。**用身份和曝光换供给，不用现金**

**第 2 步：再引需求（小红书为主战场）**

- 内容形态：以伦敦真实需求单和完成案例做成"我在伦敦喊了一声，真有人来了"的图文（这正是 5.2 能力 #10 存在的运营理由——把用户的每次成功撮合变成获客素材）
- 关键词布局：伦敦搭子、伦敦一日游、伦敦地陪、伦敦拍照、留学生二手
- 转化路径：小红书图文 → 评论区/主页引导 → 小程序体验版二维码

### 11.2 持续运营（每日 <30 分钟）

- 小螺自动生成每日城市话题与每周精华摘要（5.2 能力 #12），组长只需确认发布
- 待审队列与举报队列处理（目标 <20 分钟/天）
- 每周复盘三个数：成功撮合数、首响率、响应者留存
- 对无人响应的需求单人工兜底一次（个人开发者亲自回答），这既是留存挽回也是语料积累

**在 PRD 里写清"不做什么"和写清"做什么"同样重要**——它是产品边界的声明，也是后续需求评审时抵御功能蔓延的依据。

## 附录 A：命名候选评估

### A.1 中文名：喊呗 vs 海螺

最终候选为「喊呗」与「海螺」，结论是选用喊呗，海螺下沉为品牌资产（AI 助手「小螺」+ 吉祥物 + 品牌故事）。

| 评估维度 | 喊呗 | 海螺 |
|---|---|---|
| 语义直白度（听到即懂） | 强：直接对应"喊人"这一核心动作 | 弱：无法从名字推断产品用途 |
| 可动词化传播 | 强："上喊呗喊一个" | 弱：只能说"用海螺" |
| 场景覆盖 | 搭子/帮忙/借物/应急均自然成立 | 语义与具体场景无关联 |
| 搜索独特性 | 高：语气词组合独特 | 低：海螺水泥、海螺沟占据认知位 |
| 场景方向一致性 | 中性 | 冲突："海"指向海岛度假，产品是欧美城市 |
| 心理门槛 | "呗"带来随意感，降低求助的心理负担 | 中性 |
| IP 形象潜力 | 中 | **强**：可做极佳吉祥物 |
| 听感 | 口语、略糙 | **圆润优雅** |
| 教育成本 | 极低 | 高（零预算项目负担不起） |

海螺胜出的两项（IP 潜力、听感）对一个依赖"被搜到、被理解、被口头转述"的冷启动产品，价值远低于喊呗胜出的三项（语义直白、可动词化、搜索独特）。而通过把海螺下沉为吉祥物与 AI 助手命名，这两项优势被完整保留——**两者不必二选一**。

### A.2 英文名：HeyBay vs CallBay vs Holler

结论：**HeyBay**。同时作为代码仓库与目录名（`heybay`）。

- **CallBay（不选）**：`call` 在产品语境中会被理解为通话、客服、呼叫中心，而本产品的核心动作是"发需求单"而非"打电话"，语义方向偏移。另有中文谐音风险（"靠北"）。
- **Holler（不选）**：语义最准（英语口语"喊一声"），但对中文母语用户识别度低、拼写易错，不利于口头传播与搜索。保留为英文 Slogan 用词。
- **HeyBay（选用）**：`Hey` 准确对应"喊/打招呼"，是全球通用度最高的招呼语；`Bay`（港湾）与品牌故事中的"陌生海岸、螺号呼应"形成呼应，可解释为"旅行者落地后的港湾"。拼写简单、双音节、易记、域名与账号可用性较好。

**命名一致性要求**：中文名喊呗、英文名 HeyBay、AI 助手小螺、仓库名 `heybay` 四者构成一套，文档、代码、小程序名、社媒账号必须统一使用，不再出现其他英文名变体。


## 附录 B：术语表

- **需求单（Request）**：产品的原子单位。一个有明确诉求、明确时效、可被接受、可被完成、可被评价的对象。
- **约定单（Agreement）**：选定响应者后自动生成的只读共识凭证。平台托管共识，不托管资金。
- **本地响应者**：当地常驻的华人/留学生/长期旅居者，构成城市供给池。
- **喊呗信任分**：由基础身份、自证、履约、社区背书四层构成的 0~100 分值，对外展示为四档徽章 + 证据清单。
- **小螺**：产品内 AI 助手的名称，同时是底层 AI 能力的统称。
- **自主性阶梯（L0~L3）**：小螺对外行动权限的四个档位，由用户选择，默认 L1。
- **兜底作答**：需求单无真人响应时，小螺基于城市语料 RAG 给出的答案，明确标注来源与"请核实"。
- **小组健康度**：城市下兴趣小组的周度健康评分，低于阈值将被降权、合并或归档。
- **开城标准**：复制到下一座城市前必须同时满足的四项量化门槛。
- **Demo A / Demo B**：分别为"可真实使用的完整版（体验版发布）"与"升级路径演示原型"。

## 附录 C：待确认事项

以下事项在开发启动前必须逐项核实，任何一项的结论变化都会影响方案：

1. 微信小程序个人主体的类目限制与 UGC 功能禁区的**当期**具体规则（以微信公众平台官方文档为准）
2. 微信小程序**体验版的体验成员数量上限**与内容合规要求
3. 微信订阅消息的一次性/长期订阅规则与当期类目要求
4. iOS 端虚拟权益的当期规则，以及"引导至站外购买"的可行性边界
5. "喊呗"的小程序名称占用情况与商标可注册性（含近似查询）
6. 英国/欧盟 GDPR 下面向欧洲用户的隐私政策具体披露要求
7. 所选模型 API 的当期价格与并发限制，据此复核 5.6 的成本估算
8. 是否需要为体验版用户提供独立的数据删除与导出入口
