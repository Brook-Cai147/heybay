# 实施计划（Implementation Plan）— M1「跑通主干」

> **范围**：M1（M1-01 ~ M1-19，19 步）与 M2（M2-01 ~ M2-16，16 步）。**M3 及以后不在本文件内。**
> **M1 在整体排期中的位置**（2026-08-29 调整，D-32）：M1 是"能跑的主干"，不含任何 AI；**AI 主干是紧接着的 M2**（`aiGateway`、需求单解析与降级、小螺对话页与工具编排、L0/L1 自主性阶梯、关键词兜底、离线评测集）。M1 的每一处设计都要为 M2 留好接口，尤其是发布页（M2 只替换"帮我整理"这一个动作）与四类字段不可代填的服务端校验（M1 就立住，M2 不用回头改）。
> **执行约定**：按 `CLAUDE.md` 的五条强制规则，一次只推进一步；每步在 `step/M1-xx-<简短描述>` 分支上做，完成时同步更新 `architecture.md`、追加 `progress.md`、提交带步骤编号的 commit。
> **本计划不含代码**，只含指令。实现时的具体写法由执行会话决定，但不得违反 `architecture.md` 的分层铁律。

## M1 明确不做（避免顺手扩范围）

AI 解析与 `aiGateway`（M2）、小螺对话页（M2）、关键词兜底作答（M2）、三层机审 `moderation`（M3）、约定单 `agreements`（M3）、双向评价 `reviews`（M3）、1v1 私信（M3）、信任分计算（M3）、城市社区页与帖子流（M3）、**订阅消息（模板/授权/发送三件事一起放 M4，见 D-30 的撤回记录）**、管理员页面与数据看板（M4）、搜索页、`stats` 预聚合、**A/B 实验配置与对比分析（M5，等有真实用户，见 D-31）**。M1 的发布页就是「纯表单形态」——它同时是 D-15 里 AI 失败后的降级路径，先把降级路径做对，M2 再把 AI 叠上去。

M1 的状态机终点是 `done`，不做 `rated`（评价属 M2）。

## 已确认的执行前提（2026-08-29 逐条确认，冲突已消解）

1. **枚举双份，云侧为权威**，用 parity 单测锁住漂移（D-27）。
2. **云函数只在微信开发者工具里上传**，不引入 CloudBase CLI；代价是云侧步骤独占工具、并行窗口只剩前五步（D-28）。
3. **单测范围放宽到五块**：状态机、AI 额度、分发频控、过期判定、A/B 分桶与枚举一致性（D-29）。
4. **M1 不做订阅消息**（D-30 已撤回原「只收授权」方案：`requestSubscribeMessage` 必须传 templateId，做不到"不申请模板只收授权"；且零用户下授权率数据无意义）。模板、授权、发送三件事一起归 M4。
5. **身份采集**：不采手机号，纯微信授权登录 + 自填性别；未填性别不能响应「仅同性」单（D-26）。
6. **埋点只做"数据不缺失"**：事件字典 + 分桶字段照做，但**不做实验配置、分组比例、对比分析**（D-31，推后到 M5）。AI 质量在 M2 用离线评测集证明，不靠真实流量 A/B。
7. **云环境 ID 写进代码并入库**：客户端必须知道它才能 `cloud.init`，反编译体验版即可见，它不是密钥——安全性靠 M1-07 的权限收紧与云函数鉴权，不靠隐藏。落在 `miniprogram/config/env.js` 一处常量，另在 `progress.md` 记一份便于查阅。真正的密钥（AI Key、AppSecret）仍只在云函数环境变量。
8. **V1.0 旧页面不删**，M1-14 只从路由与 tabBar 摘除，文件保留作重构对照。
9. **联调用开发者工具的多账号调试**，不为 M1 发体验版、不加体验成员。
10. **在架上限 M1 对所有人按 3 条**，数值放 `configs`，会员的 10 条归 M5。
11. **基础库保持 3.15.0**，不做版本调整（见 `progress.md`）。

# M1「跑通主干」

## M1-01 需求单状态转移表与测试骨架

- **目标**：建立仓库根的 `node:test` 运行入口，并实现 PRD 4.1 状态机的转移表与合法性校验（纯函数，不接触数据库）。
- **涉及文件**：`package.json`（新建，仅用于 test 脚本，不引入运行时依赖）、`cloudfunctions/_shared/constants/enums.js`（新建，先只放需求单状态）、`cloudfunctions/_shared/service/requestStateMachine.js`（新建，只含转移表与 `canTransition` 判定）、`tests/requestStateMachine.transitions.test.js`（新建）
- **前置依赖**：无
- **具体指令**：
  1. 在仓库根建 `package.json`，`private: true`，`scripts.test` 指向 `node --test "tests/**/*.test.js"`（**不要写 `node --test tests/`**——Node 26 会把目录当模块加载并报 `Cannot find module`），不装任何第三方依赖。
  2. 在 `enums.js` 里定义九个需求单状态（draft / open / responded / matched / done / cancelled / expired / removed / rated），与 `tech-stack.md` 第 3 节的转移表键名逐字一致；`rated` 只登记不在 M1 使用。
  3. 在 `requestStateMachine.js` 里把 `tech-stack.md` 第 3 节的 `TRANSITIONS` 表原样落地为显式常量，并提供一个只判断「from→to 是否合法」的纯函数；非法转移抛出带 from/to 的错误，不返回布尔以外的模糊值。
  4. 测试至少覆盖：全部合法转移逐条通过；终态（rated / expired / cancelled / removed）任何出边都被拒；未知状态被拒；`draft` 不能直接跳 `matched`。
- **验证方式**：纯逻辑步骤 → 运行 `npm test`，贴出用例数与通过数。
- **完成标志**：`npm test` 全绿，且转移表里的每一条边都有对应用例。
- **并行冲突**：不占开发者工具；不写云数据库。与 M1-02（同一状态机文件）、M1-03（同一 enums 文件）有文件交集，**不可与这两步并行**。

## M1-02 状态机的角色权限矩阵

- **目标**：在转移表之上加一层「谁能做这次转移」的权限矩阵，让 `transitionRequest` 的鉴权判断成为可测试的纯逻辑。
- **涉及文件**：`cloudfunctions/_shared/service/requestStateMachine.js`（扩展）、`tests/requestStateMachine.permissions.test.js`（新建）
- **前置依赖**：M1-01
- **具体指令**：
  1. 定义四种 actor 角色：需求方 owner、响应者 responder、系统 system（定时任务）、管理员 admin。
  2. 为每条合法转移标注允许的角色：发布（owner）、被响应（system，由响应动作触发）、选定（owner）、完成（owner 与 responder 双方各自确认，任一方单独确认不足以进 done，本步只需把「谁有资格确认」判出来，双方确认的计数逻辑在 M1-12）、取消（owner 或 responder，需记录取消方）、过期（仅 system）、下架（仅 admin）。
  3. 提供一个纯函数，输入 from/to/actor 角色，输出允许或抛错；错误信息要能区分「转移非法」与「转移合法但你没权限」两种情况，便于前端提示。
  4. 测试覆盖：每个角色的允许集逐条通过；至少 8 条越权用例被拒（如 responder 选定自己、owner 让单子过期、responder 下架、admin 之外的角色下架）。
- **验证方式**：纯逻辑步骤 → 运行 `npm test`，贴出用例数与通过数。
- **完成标志**：权限矩阵的每个格子（合法转移 × 四角色）都有用例，越权用例全部为拒。
- **并行冲突**：不占开发者工具；不写云数据库。与 M1-01 共用同一状态机文件，**必须在 M1-01 合回 main 后再开**；与 M1-04、M1-05 无交集，可并行。

## M1-03 端侧枚举与字段校验，并锁定两份枚举一致

- **目标**：把 PRD 4.1 的字段规则落成端侧校验模块，同时用测试锁住云侧与端侧枚举不漂移。
- **涉及文件**：`miniprogram/models/enums.js`（新建）、`miniprogram/models/schema.js`（新建）、`cloudfunctions/_shared/constants/enums.js`（补充品类等枚举）、`tests/enumsParity.test.js`（新建）
- **前置依赖**：M1-01
- **具体指令**：
  1. 在云侧 `enums.js` 补齐：8 类品类白名单、时效类型（预约型 / 即时型及 1h/3h/今天内）、报酬类型（免费互助 / 请一顿 / 付费 / 以物换物）、可见范围、性别（男 / 女 / 未填，仅供「仅同性响应」判定，见 D-26）、偏好开关（**只允许「仅同性响应」，禁止出现任何异性偏好键，见 D-09**）。
  2. 端侧 `enums.js` 保持同名同值，文件头注明「权威副本在云侧，任何改动必须两侧同步」。
  3. `schema.js` 只做体验层校验：必填项（品类/城市/标题/详情/时效/报酬类型）、标题 ≤20 字、图片 ≤9 张、付费时金额必填、搭子类人数必填、预约型期望时间必填、地点字段命中门牌号特征时给提示（不硬拦）。校验函数返回结构化的字段级错误，不抛异常。
  4. 新增一致性测试：分别 require 两份 enums，断言状态、品类、时效、报酬四组的键与值完全相等。
- **验证方式**：混合 —— 一致性部分属纯逻辑，运行 `npm test` 贴结果；`schema.js` 属端侧模块，在微信开发者工具控制台调用 3 个正例与 3 个反例（缺品类、标题超长、付费无金额），贴出返回的字段级错误对象。
- **完成标志**：`npm test` 全绿；控制台 6 次调用的返回值与预期一致并贴出。
- **并行冲突**：**占用开发者工具**（仅控制台调用，几分钟）；不写云数据库。与 M1-01/M1-02 共用云侧 `enums.js`，不可与其并行；与 M1-04、M1-05 无文件交集。

## M1-04 A/B 分桶与埋点事件字典

- **目标**：把分桶纯函数与事件字典做出来，保证将来有真实用户时历史数据不缺失（D-21）；**不做实验运营**（D-31）。
- **涉及文件**：`cloudfunctions/_shared/service/bucketing.js`（新建）、`cloudfunctions/_shared/constants/events.js`（新建）、`tests/bucketing.test.js`（新建）
- **前置依赖**：无
- **具体指令**：
  1. 分桶函数：输入 openid 与实验 key，输出 0~99 的桶号；同一 openid + 同一实验 key 必须永远落同一桶（纯函数，不读数据库、不用随机数、不用当前时间）。
  2. **M1 只用一个固定的默认实验 key**（例如 `default`），把桶号当作"用户的稳定随机标识"埋进每条事件即可；分组比例、实验配置读取、多实验并存等留到 M5——当前零用户，做了没有产出（D-31）。
  3. 事件字典按 PRD 7.3 的六类分组登记事件名与必填参数：需求单状态变更、AI 调用（M1 先占位，M2 由 `aiGateway` 填满）、分发触达与响应归因、增信任务漏斗（占位）、安全功能使用率、分桶标识。事件名一旦上报即视为冻结，本步要在文件头写明这条纪律。
  4. 测试覆盖：同一 openid 多次调用桶号稳定；不同 openid 分布大致均匀（1000 个构造 openid 检查偏差在合理范围）；不同实验 key 分布不相关。
- **验证方式**：纯逻辑步骤 → 运行 `npm test`，贴出用例数与通过数。
- **完成标志**：`npm test` 全绿；事件字典覆盖 PRD 7.3 六类且每类至少一个具体事件名。
- **并行冲突**：不占开发者工具；不写云数据库。与其他任何步骤无文件交集，**是最理想的并行槽位**。

## M1-05 需求单过期判定

- **目标**：把 PRD 4.1 的过期规则做成纯函数，供 M1-18 的定时任务调用。
- **涉及文件**：`cloudfunctions/_shared/service/requestExpiry.js`（新建）、`tests/requestExpiry.test.js`（新建）
- **前置依赖**：无
- **具体指令**：
  1. 规则：预约型在期望时间之后 24 小时过期；即时型按有效时长（1h / 3h / 今天内）过期，「今天内」以需求单所属城市的当地日期为界。
  2. 函数签名必须把「当前时间」作为显式入参传入，不在函数内部取系统时间——否则无法测试。
  3. 同时提供「同一用户同城在架上限」的判定纯函数：免费用户 3 条、会员 10 条（PRD 4.1 规则 4），只判断给定在架数量是否超限，不查库。
  4. 测试覆盖：边界前一秒不过期、边界后一秒过期、跨时区的「今天内」、缺失期望时间的预约型按数据异常处理、在架上限的等于/超出两种情况。
- **验证方式**：纯逻辑步骤 → 运行 `npm test`，贴出用例数与通过数。
- **完成标志**：`npm test` 全绿，含至少 4 条时间边界用例。
- **并行冲突**：不占开发者工具；不写云数据库。与其他任何步骤无文件交集，可与 M1-04 或任一占工具的步骤并行。

## M1-07 建集合、建索引、收紧权限

- **目标**：把 M1 需要的六个集合建好，索引与唯一约束一次建对，权限全部收成「仅云函数可写」。
- **涉及文件**：无代码文件；产出为 `memory-bank/architecture.md` 里新增的「集合与索引清单」小节（追加，不重写）
- **前置依赖**：M1-06
- **具体指令**：
  1. 建集合：`users`、`requests`、`responses`、`statusLogs`、`events`、`configs`。M1 不建其余集合。
  2. 建索引，按 `tech-stack.md` 第 4 节（字段名按 D-33 一律用 openid 系列）：`users.openid` 唯一；`requests` 建 `city + status + expireAt` 与 `ownerOpenid + status`；`responses` 建 `requestId`、`responderOpenid + createdAt`，以及 **`requestId + responderOpenid` 唯一索引（幂等的物理保证，必须建，事后补要先清脏数据）**；`statusLogs` 建 `requestId + createdAt`；`events` 建 `openid + createdAt` 与 `name + createdAt`；`configs.key` 唯一。共 10 条。
  3. 六个集合的权限**全部**设为「仅管理端可读写」（此控制台版本的档位名为**「所有用户不可读写」**，横幅注明「云控制台和服务端始终有所有数据读写权限，以下配置仅对小程序端发起的请求有效」，即云函数不受影响）。绝不使用「所有用户可读」或「所有用户可读写」。设置完把每个集合的权限档位名抄进 `progress.md`。
  4. 在 `configs` 里写入两条初始配置：管理员 openid 白名单（`key: 'admin_openids'`）、伦敦城市配置（`key: 'city_london'`，含 `timeZone: 'Europe/London'` 与在架上限，见 D-34）。这两条是真实配置，**不带 `_isTest`**。A/B 实验配置留到 M5（D-31）。**写入方式用云函数的 `seedConfigs` 动作，不手工敲控制台**——`configs` 权限已收成端侧不可写，云函数是唯一合法写入方；管理员 openid 直接取调用上下文，避免人肉复制出错；换环境时能一键复现。函数内做幂等（按 key 查，有则更新无则新建）。
  5. 明确写下 `_isTest` 纪律：本阶段所有手工写入的数据都带 `_isTest: true`。
- **验证方式**：数据库步骤 → 从小程序端**直接**尝试写一次 `requests`（预期被权限拒绝），贴出报错原文；再用 `ping` 之外的任意云函数写一条 `_isTest` 数据并贴出返回的 `_id`。两条都要贴。
- **完成标志**：端侧直写被拒有报错原文为证；索引清单已追加进 `architecture.md`。
- **并行冲突**：**独占开发者工具与云环境**；**写云数据库（改结构）**。风险最高的一步，执行期间另一路只能做纯逻辑步骤。与 M1-08 起的所有云步骤强依赖，不可并行。

## M1-08 dao 层与登录建档云函数

## M1-09 requestFlow 云函数与发布动作

- **目标**：建立需求单唯一写入口，跑通 draft→open，并让服务端二次校验四类不可代填字段。
- **涉及文件**：`cloudfunctions/requestFlow/index.js`（新建 handler）、`cloudfunctions/_shared/service/requestService.js`（新建）、`miniprogram/services/request.js`（新建）
- **前置依赖**：M1-01、M1-02、M1-03、M1-08
- **具体指令**：
  1. handler 只做三件事：取 OPENID、校验入参形状、按 action 分发到 service。业务判断一律不写在 handler 里。
  2. 唯一状态变更入口命名为 `transitionRequest`，签名为 requestId + 目标状态 + actor；`create` 动作内部也走一次 draft→open 的转移校验，不绕过状态机。
  3. 服务端必须独立再校验一遍字段（不信任端侧 `schema.js`），并额外校验 PRD 5.4 的四类字段来源标记：金额、见面时间、见面地点、联系方式若标记为 AI 生成则拒绝写入（M1 还没有 AI，但校验先立住，M2 才不用回头改）。
  4. 每次成功转移都写一条 `statusLogs`（requestId、from、to、actor、原因），与需求单更新在同一次调用内完成；写日志失败要让整个动作失败，不允许状态变了而无审计。
  5. 校验「同城在架上限」时调用 M1-05 的纯函数，不在 service 里重写规则；**M1 对所有人按 3 条**，数值从 `configs` 读（会员的 10 条归 M4，届时改配置不改代码）。
- **验证方式**：云函数步骤 → 调用一次发布，贴出返回的 requestId 与 `statusLogs` 里对应记录的真实内容；再调用一次带 AI 来源标记金额的发布，贴出被拒的报错原文。
- **完成标志**：两次调用的真实返回值都已贴出；`requests` 里新单状态为 open 且带 `_isTest`。
- **并行冲突**：**占用开发者工具**；**写云数据库**。与 M1-10~M1-12 共用 `requestFlow` 与 `requestService`，属同一文件族，**这四步必须串行**。

## M1-10 响应动作与幂等

- **目标**：跑通「响应者响应需求单」，并让重复提交在数据库层面无法造成第二条响应。
- **涉及文件**：`cloudfunctions/responseFlow/index.js`（新建）、`cloudfunctions/_shared/service/responseService.js`（新建）、`miniprogram/services/response.js`（新建）
- **前置依赖**：M1-09
- **具体指令**：
  1. 响应动作写入 `responses`（含一句话自荐、付费类的报价、来源归因字段：推送 / 社区 / 邀请 / 广播），并冗余存响应者昵称、头像、信任档位（`tech-stack.md` 第 4 节：冗余优于联查）。
  2. 首个响应触发需求单 open→responded，转移必须经 `transitionRequest`，actor 为 system；已是 responded 的单再来响应不重复转移。
  3. 幂等靠 `requestId + responderOpenid` 唯一索引兜底：捕获唯一键冲突并转成「你已响应过」的业务返回，不向端侧抛原始数据库错误。
  4. 拒绝三类响应：响应自己的单、单子不在 open/responded 状态、需求单开了「仅同性响应」而响应者性别不符或未填（未填时返回「补全性别后可响应」，见 D-26，不是笼统报错）。

- **验证方式**：云函数步骤 → 用另一个 openid 响应一次，贴出返回值与需求单变更后的状态；同一 openid 再响应一次，贴出幂等提示的真实返回；响应自己的单，贴出被拒报错。

- **并行冲突**：**占用开发者工具**；**写云数据库**。与 M1-09、M1-11、M1-12 同属状态流转文件族，必须串行；与 M1-15/M1-16/M1-17 有 `miniprogram/services/` 目录交集（不同文件，冲突面小）。
