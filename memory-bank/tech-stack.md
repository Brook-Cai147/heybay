# 喊呗 HeyBay 技术栈选型

> 配套文档：`memory-bank/design-document.md`（V2.0 完整 PRD）
> 选型约束：个人开发者、业余时间、资金投入近 0、需真实可用、需作为作品集展示。
> 选型原则：**简单优先，健壮靠边界而非靠框架。** 每一项技术都要能用"它替我省掉了什么必须自己做对的事"来解释；省不掉的就不引入。

---

## 0. 结论速览

| 层 | 选型 | 一句话理由 |
|---|---|---|
| 客户端 | 微信小程序原生（glass-easel，JS） | V1.0 已是原生代码，单端交付，无跨端需求 |
| 后端 | 微信云开发 CloudBase 云函数 | 免运维，且**免费拿到可信身份 openid** |
| 数据库 | 云开发云数据库（文档型） | 与云函数同生态，零配置，够用 |
| 文件 | 云存储 | 图片直传 + CDN，无需自建 |
| 实时消息 | 云数据库实时推送（watch） | 不自建 WebSocket，零运维 |
| 触达 | 微信订阅消息（一次性） | 唯一免费的主动触达通道 |
| AI 调用 | 云函数内的 `aiGateway` 统一网关 | 密钥不落端，额度/成本/降级集中管控 |
| 模型 | DeepSeek / 豆包 / Qwen 便宜档 | 中文场景够用，成本比贵档低一到两个数量级 |
| 检索 | 关键词 + 标签过滤起步，暂不上向量库 | 冷启动语料量不值得引入向量检索 |
| 内容安全 | 微信内容安全接口 + 本地词表 + 模型语义审核 | 三层，前两层免费且必须 |
| 运营后台 | 小程序内的管理员页面（openid 白名单） | 零额外部署，省掉一整套 Web 后台 |
| 埋点/AB | 自建 events 集合 + 定时预聚合 | 满足 PRD 第 7 章指标即可，不引入第三方 SDK |
| 定时任务 | 云函数定时触发器 | 需求单过期、日报周报、健康分 |
| 测试 | Node 内置 `node:test`，只测纯逻辑 | 状态机与额度计算必须有测试，UI 不测 |
| 代码质量 | ESLint + Prettier | 轻量配置，不上 TypeScript 全量迁移 |

## 1. 客户端：继续用微信小程序原生

**选它的理由**

1. `miniprogram/` 里已经是一份可运行的原生小程序（`app.json` 声明 11 个页面 + `custom-tab-bar` 自定义 tabBar，`componentFramework: glass-easel`，`lazyCodeLoading: requiredComponents`）。改造成本远低于重写。
2. 交付目标只有一个端（微信小程序体验版，见 PRD 9.3），跨端框架的唯一价值——多端复用——在这里为零。
3. 原生对小程序 API（订阅消息、内容安全、云开发、分享、剪贴板）的支持没有中间层，出问题时可直接查官方文档，不用先判断是框架的 bug 还是平台的 bug。这对只有一个人排查问题的项目很重要。

**明确不用 Taro / uni-app**：会引入 Node 构建链、版本兼容矩阵和一层调试隔离，换来的跨端能力用不上。这是本项目最容易犯的过度工程。

**不做 TypeScript 全量迁移**，但要拿到类型系统的主要收益：

- 所有状态、品类、角色等枚举值集中在 `miniprogram/models/enums.js`，禁止在业务代码里写字符串字面量
- 数据模型的字段校验集中在 `miniprogram/models/schema.js`，提交前本地先校验一遍（服务端仍会再校验，前端校验只为体验）
- 公共函数用 JSDoc 标注参数与返回值，编辑器即可获得补全与提示

理由：小程序 + TS 需要额外构建配置，而本项目的 bug 主要来源不是类型错误，是**状态流转和权限判断**——那要靠第 3 节的服务端边界解决，不是靠类型。

## 2. 后端：微信云开发（CloudBase）

**核心理由不是"免运维"，是"免费拿到可信身份"。**

云函数被小程序调用时，运行上下文里直接带着微信校验过的 `OPENID`。这意味着注册、登录、会话、token 刷新、防伪造这一整套最容易写出安全漏洞的东西**完全不用自己写**。对一个业余时间开发、又要处理陌生人线下见面这种高信任要求场景的项目，这是决定性的收益。

次要理由：无服务器运维、无需备案独立域名、有免费额度、云函数/数据库/存储同生态零配置互通。

**免费额度的实际结论（2026-08 核实）**：自 2025-02-19 起，每个无云环境的小程序账号可创建 1 个免费云环境，**在小程序未发布上线阶段无需续费**；正式上线后到期时间变更为上线后第 15 天。免费环境配额与基础套餐一致（调用 20 万次/月、容量 2GB、云函数外网出流量 2GB、云函数资源 10 万 GBs、CDN 5GB、QPS 500），不支持加购资源包与按量付费。基础套餐 ¥19.9/月。

由于本项目按第 9.3 节只发**体验版、不走正式上线**，免费环境可覆盖全部开发与小范围真实运营，**云开发实际成本为 0**。这也是第 8.3 节"月运营成本控制在 200 元以内"能成立的主要原因。需注意 IDE 内文案与官方文档口径不一致，开通后应立即在云开发控制台确认实际到期时间。

**开通时机**：V1.0 代码不含任何云能力调用，导入项目时可先选"不使用云服务"，等 M1-01（云开发环境初始化）真正开始时再在项目设置里补开。这样可避免在只写文档的阶段空耗任何计时类额度。

**被否决的替代方案**

- **自建 Node + 云服务器**：要买服务器、要备案域名、要自己实现小程序登录换 session、要配 HTTPS、要做进程守护与日志。每一项都是可能出错的地方，换来的只是"技术栈更通用"。
- **Supabase / Firebase**：Auth 与小程序登录体系对不上，仍要自己搭一层身份映射；国内访问稳定性不可控。
- **纯前端 + 本地存储**：无法支撑撮合（需要跨用户共享数据），直接不可行。

**已知代价与缓解**

绑定微信生态，将来若要做 App 或 Web 端，后端要重写。缓解办法是**从第一天就分层**：

```
云函数 (handler)  ← 只做参数校验、鉴权、调用 service
    └── service/  ← 全部业务逻辑，不直接写数据库语句
            └── dao/  ← 唯一接触云数据库 API 的地方
```

业务逻辑不散落在小程序端、也不散落在数据库查询里。真要迁移，换掉 `dao/` 和 handler 外壳即可。

**环境策略**：云开发免费额度通常只够一个环境。初期用**单环境 + Feature Flag**（`configs` 集合）区分开发中与已上线的功能，联调数据统一打 `_isTest: true` 标记并在正式查询里排除。这比申请两套环境省钱，代价是必须严格遵守"任何写操作都带 `_isTest` 字段"的纪律。

## 3. 健壮性的真正来源：服务端边界

这一节是整份技术栈里最重要的部分。本产品的核心风险不是性能，是**状态被改坏、权限被绕过、钱数被篡改**。做法只有一条铁律：

> **前端不可信。所有状态变更只能通过云函数的单一入口，前端永远不能直接写 `status` 字段。**

具体实现：

**（1）数据库权限收紧**。所有业务集合的权限设为"仅管理端可写"（即只有云函数能写），小程序端只有读权限，且读权限通过云函数或安全规则限制到必要字段。绝不使用"所有用户可读写"。

**（2）需求单状态机集中管控**。PRD 4.1 定义的状态流转，实现为一张显式的转移表：

```js
// service/requestStateMachine.js
const TRANSITIONS = {
  draft:     ['open'],
  open:      ['responded', 'expired', 'cancelled', 'removed'],
  responded: ['matched', 'expired', 'cancelled', 'removed'],
  matched:   ['done', 'cancelled'],
  done:      ['rated'],
  rated:     [],
  expired:   [],
  cancelled: [],
  removed:   [],
}
```

唯一的写入口 `transitionRequest(requestId, toStatus, actor)` 负责：校验转移是否合法 → 校验 actor 是否有权做这次转移（需求方 / 响应者 / 系统 / 管理员各自能做哪些）→ 写入并追加一条 `statusLogs` 记录。非法转移直接抛错。

这张表和它的权限矩阵**必须有单元测试**（第 10 节），因为它是全产品最容易出隐蔽 bug 的地方，而线上出错会直接导致用户纠纷。

**（3）金额与身份字段服务端二次校验**。PRD 5.4 规定 AI 不可代填金额、时间、地点、联系方式；服务端要独立再校验一次这些字段的来源标记，防止前端绕过。

**（4）幂等**。响应、选定、确认完成、评价这四个动作都要幂等（用 `requestId + userId + action` 唯一索引），避免用户网络重试造成重复响应或重复评价。

## 4. 数据模型

云数据库为文档型，按聚合边界设计集合，避免多集合联查（文档型数据库的联查能力弱且慢）。

| 集合 | 用途 | 关键索引 |
|---|---|---|
| `users` | 账号、信任分、能力标签、常驻城市、会员状态 | `openid`（唯一） |
| `requests` | 需求单主体（PRD 4.1 全部字段） | `city + status + expireAt`、`ownerId + status` |
| `responses` | 对需求单的响应（含报价、自荐语） | `requestId`、`responderId + createdAt`、`requestId + responderId`（唯一，保证幂等） |
| `agreements` | 约定单（只读共识凭证，含版本历史） | `requestId`（唯一） |
| `reviews` | 双向评价 | `targetUserId`、`requestId + raterId`（唯一） |
| `posts` | 社区内容 | `city + partition + createdAt` |
| `groups` | 兴趣小组 + 健康分 | `city + healthScore` |
| `cities` | 城市配置（紧急号码、使领馆、官方分区、开城状态） | `code`（唯一） |
| `reports` | 举报 | `status + priority + createdAt` |
| `statusLogs` | 需求单状态变更审计 | `requestId + createdAt` |
| `aiLogs` | AI 调用记录（能力、耗时、token、是否被采纳/修改） | `userId + createdAt`、`capability + createdAt` |
| `events` | 埋点 | `userId + createdAt`、`name + createdAt` |
| `stats` | 定时预聚合的看板数据 | `date + metric` |
| `configs` | Feature Flag、A/B 实验、额度配置、管理员白名单 | `key`（唯一） |
| `knowledge` | 城市语料库（社区精华 + 过期需求单的问答对） | `city + tags` |

**集合命名统一驼峰**（`statusLogs`、`aiLogs`），不用下划线，避免同一集合出现两种写法。

**冗余优于联查**：`requests` 里冗余存需求方的昵称、头像、信任档位；`responses` 里冗余存响应者的同类字段。文档型数据库下这是正确做法，代价是用户改昵称时需要一个定时任务回填（可接受，甚至可以不回填——历史快照反而更真实）。

**软删除**：所有集合用 `deletedAt` 软删除，不做物理删除。理由是纠纷追溯需要证据。例外是 GDPR 的账号删除请求，那种情况要真删或匿名化（见第 9 节）。

## 5. 实时消息与触达

**1v1 私信不自建 WebSocket。** 用云数据库的实时推送（`collection.where(...).watch()`）监听会话集合。理由：自建长连接意味着要买服务器、做心跳、做断线重连、做水平扩展——而 PRD 10 已明确私信实时性要求可放宽到秒级。降级方案是前台轮询（3~5 秒），在 watch 连接失败时自动切换。

**触达只有一条免费通道：微信订阅消息（一次性订阅）。**

这是技术选型里最需要产品配合的一处约束：**一次用户授权只能换一条推送**。因此必须在产品流程里顺势收集授权，而不是设置页里放个开关：

- 发布需求单成功时 → 请求授权（用于"有人响应了"）
- 收到首个响应时 → 请求授权（用于"响应者信息更新"）
- 被选定时 → 请求授权（用于"对方确认完成"）

这直接决定了 PRD 5.3 中 L2 自动分发的触达率上限。授权率要作为埋点指标持续观察，因为它是整个即时响应链路的天花板。

**排期**：订阅消息整块（模板申请 + 授权收集 + 发送）放在 M4 一起做，M1~M3 不碰（D-30）。原因是 `requestSubscribeMessage` 必须传 templateId，"只收授权不申请模板"在技术上不成立；而授权率这个指标在零真实用户阶段也拿不到有效数据（D-31）。

## 6. AI 架构

### 6.1 统一网关 `aiGateway`

所有 AI 能力（PRD 5.2 的 14 项）**只有一个云函数出口**。这是 AI 侧健壮性与成本可控的唯一保证。

```
小程序 → aiGateway(capability, payload)
             ├── 1. 鉴权：openid
             ├── 2. 额度检查：configs 里的免费/会员额度（PRD 5.6）
             ├── 3. 缓存查询：同城市同问题的近期结果直接复用
             ├── 4. Prompt 组装：capability → prompt 模板 + RAG 上下文
             ├── 5. 模型调用：超时 8s，失败重试 1 次
             ├── 6. 输出校验：JSON Schema 校验，不合格重试 1 次
             ├── 7. 降级：仍失败 → 返回结构化的"降级信号"，前端切普通表单
             └── 8. 记账：写 aiLogs（耗时、token、成本、是否被采纳）
```

**密钥管理**：模型 API Key 只存在云函数的环境变量里，永不出现在小程序代码、`project.config.json` 或 git 仓库中（`.gitignore` 已排除 `.env` 与 `project.private.config.json`）。

**模型选型**：主力用 DeepSeek / 豆包 / Qwen 的便宜档。理由见 PRD 5.6 的成本测算——需求单解析这类短文本任务单次成本在千分之几元，而它是全产品调用量最大的能力。不为了"用更好的模型"把一个能免费给的功能变成付费墙。

**结构化输出**：需求单解析这类必须拿到确定结构的能力，用 JSON Schema 约束输出并在网关侧校验。校验失败重试一次，仍失败就降级为普通表单——**AI 失败绝不能阻断用户发布需求**，这是 PRD 5.4 "可回退"护栏的技术落点。

### 6.2 检索：先不上向量数据库

冷启动期语料只有几百条（PRD 4.7 的 30 条内容 + 100 条问答 + 逐步累积的过期需求单）。这个量级下：

- **起步方案**：`knowledge` 集合按 `city + tags` 过滤 + 关键词匹配，取 Top 5 塞进 prompt。够用、零额外成本、零额外组件。
- **升级触发条件**：单城语料超过约 2000 条，或关键词检索的兜底采纳率（PRD 5.5 指标）跌破 50%。届时再引入向量检索。

在几百条语料上引入向量数据库是典型的过度工程——它增加一个必须维护的组件、一份必须同步的索引，而检索质量提升在这个量级上几乎观察不到。

### 6.3 内容安全：三层，前两层免费

1. **微信内容安全接口**（`security.msgSecCheck` / `imgSecCheck`）：免费且**必须接**，这是平台合规要求，也是过审的前提。
2. **本地词表**：云函数内的关键词与正则表，覆盖 PRD 4.6 的反擦边交友规则（"仅限异性""长期关系""有偿陪伴"及变体、谐音、拼音缩写）。毫秒级、零成本。
3. **模型语义审核**：仅在前两层未命中但落在敏感品类（住宿、应急、含金额付费单）或用户信任分低于阈值时调用，控制成本。

三层的输出统一成 `pass / review / reject`，对接 PRD 4.6 的分级审核策略。

## 7. 运营后台：做在小程序里，不做独立 Web 后台

PRD 9.3 把运营后台收窄为四件事：待审队列、举报队列、用户管理、数据看板。这四件事完全可以做成**小程序内的管理员页面**，用 `configs` 集合里的 openid 白名单控制入口可见性，云函数侧再独立校验一次管理员身份（前端隐藏入口不算权限控制）。

**为什么不做独立 Web 后台**：一套 React/Vue 后台意味着额外的构建链、额外的部署、额外的鉴权体系、额外的域名与 HTTPS。而运营动作只有"看队列、点通过/驳回"，手机上做反而更顺手——PRD 11.2 的目标是每天 20 分钟处理完，手机端比开电脑更可能真的执行。

**数据看板不做实时聚合**。定时云函数每天预聚合到 `stats` 集合，看板只读预聚合结果。理由：文档型数据库的实时聚合在数据量上来后会很慢，而 PRD 7 的指标全部是天/周粒度，不需要实时。

## 8. 埋点、A/B 与定时任务

**埋点**：一个 `track` 云函数写 `events` 集合。必须覆盖 PRD 7.3 列出的六类：需求单全生命周期状态变更、AI 每次调用、分发触达与响应归因、增信任务漏斗、安全功能使用率、A/B 分桶标识。

**A/B 分桶**：`hash(openid) % 100` 落桶，实验配置放 `configs`。这是 PRD 5.5 那些"vs 纯表单 +20%""vs 纯社区展示 +30%"指标能被证明的前提——**没有分桶能力，那些指标只能是猜测**。这一项要在 M1 就做进去，事后补代价很大。

**不接第三方分析 SDK**：小程序端的第三方分析要额外域名白名单、要传用户数据出境（GDPR 风险，见第 9 节），而自建埋点在这个规模下工作量不大。

**定时触发器**（云函数 cron）：

- 每 10 分钟：即时型需求单过期扫描
- 每小时：预约型需求单过期扫描、L2 二次投放触发
- 每天：数据预聚合、城市话题生成、小组健康分计算
- 每周：精华摘要生成、开城标准达标检查

## 9. 合规相关的技术要求

对应 PRD 9.4，这些不是可选项：

- **不采集身份证件影像**（PRD 4.4）：产品里不存在证件上传入口，技术上也不预留该字段
- **不采集精确位置**：只存城市 code 与街区级文本，不调用精确定位并存储经纬度
- **不采集第三方联系人**（PRD 4.5）：行程报备用微信原生分享能力，不做"紧急联系人"数据库字段
- **社媒绑定只存结论**：只存 `platform + profileUrl + verifiedAt`，不抓取不缓存对方平台内容
- **学校邮箱验证只存结论**：只存 `verified: true + schoolName`，验证码用完即弃，不存邮箱地址本身
- **账号删除**：提供入口，执行时对 `users` 做匿名化（清空昵称头像、openid 置换为不可逆哈希）而非物理删除关联业务数据，保留纠纷追溯能力的同时满足删除请求
- **隐私政策与用户协议**：独立可访问页面，小程序内可直达，不藏在设置三级页

## 10. 测试策略：只测会造成纠纷或让数据作废的部分

不追求覆盖率，用 Node 内置的 `node:test`（零依赖）覆盖以下纯逻辑。前三块是原始范围（D-20），第 4~5 块在 M1 排期时补入、第 6 块在 M2 排期时补入（决策与判断标准见 D-29）：

1. **需求单状态机**（第 3 节）：合法/非法转移、各角色权限矩阵。这是最高优先级，因为状态错乱会直接导致用户纠纷。
2. **AI 额度与成本计算**（PRD 5.6）：免费额度、会员额度、跨天重置。算错会直接导致成本超支或误拦付费用户。
3. **分发匹配与频控**（PRD 5.4）：匹配打分、每日触达上限 3 次、静默 2 次进冷却。算错会骚扰供给端，而供给端流失是不可逆的。
4. **需求单过期判定**（PRD 4.1）：预约型 +24h、即时型按时长、"今天内"的当地日期边界。算错会导致单子永不过期，直接复活 V1.0 的死水问题。
5. **A/B 分桶与端云枚举一致性**（D-21）：同一 openid 桶号稳定、配置缺失时不入组；两份 enums 的键值完全相等。前者算错会让全部 A/B 数据作废，后者漂移会写出脏数据。
6. **AI 输出 Schema 校验**（6.1）：AI 返回值的结构校验与降级判定。校验失效会让脏数据直接进需求单，且 D-15 的"可回退"护栏形同虚设。

**不测**：UI 渲染、页面跳转、样式。手工过一遍更快。

## 12. 与 PRD 里程碑的对应

**排期原则（2026-08-29 调整，见 D-32）**：本项目的首要交付目标是 **AI 产品能力的可展示性**，其次才是运营完备度。因此 AI 主干（网关、解析、降级、评测、小螺工具编排）从原 M2 提前为独立的第二个里程碑，社区/信任/评价/安全/后台等运营向能力顺延。**当前阶段无真实用户，一切依赖真实流量的验证（A/B 实验、授权率、留存）全部推后**，改用离线评测集证明 AI 质量（D-31）。

| 里程碑 | 技术任务 |
|---|---|
| **M1** 跑通主干 | 云开发环境初始化；`users` / `requests` / `responses` / `statusLogs` / `events` / `configs` 集合与索引；`requestFlow` 状态机 + 单测；发布页（纯表单形态）与需求单详情页；需求广场最小列表；过期扫描定时任务；**埋点最小集 + 分桶字段**（只保证数据不缺失，不做实验运营，见 D-31） |
| **M2** AI 主干与小螺 | `aiGateway` 单一出口（额度、缓存、降级、成本记账）；`parseRequest` 一句话→结构化需求单并接入发布页；**JSON Schema 校验 + 重试 + 降级为纯表单**（D-15 的技术落点）；四类字段不可代填的服务端来源校验；小螺对话页 + function calling 工具编排（五个工具：`parseRequest` / `createRequest` / `searchKnowledge` / `generateChecklist` / `matchResponders`，后者产出**可解释的推荐理由**，落 PRD 5.4"不允许猜你喜欢式无理由推荐"）；自主性阶梯 L0/L1 的产品化落地（含 `draftInvite` 一键代发，D-14）；`knowledge` 集合 + 关键词检索兜底作答；**离线评测集与评测脚本**（替代真实 A/B，D-31） |

| **M4** 可上线运营 | 安全体系（拉黑/举报/行程报备/SOS）；管理员页面四件事（数据看板可暂缓）；`notify` 订阅消息模板申请 + 授权收集 + 发送（三件事一起做，授权单独提前无意义）；`stats` 预聚合；语料播种入库 |
| **M5** 商业化与作品集 | L2 自动分发 + 频控；行程清单；小红书图文；应急求助卡；会员与额度（含在架上限 3→10）；**有真实用户后再启动 A/B 实验配置与对比分析**；Demo B 原型；导出 AI 评测与决策文档 |

## 13. 明确不用的技术，及原因

| 技术 | 不用的原因 |
|---|---|
| Taro / uni-app | 只有一个交付端，跨端能力用不上，白增构建链与调试隔离 |
| TypeScript 全量迁移 | 主要 bug 来源是状态流转与权限，靠服务端边界解决，不靠类型 |
| 独立 Web 运营后台 | 运营动作只有看队列点按钮，做进小程序零部署且手机上更可能真被执行 |
| 向量数据库（初期） | 几百条语料看不出检索质量差异，却多一个必须维护同步的组件 |
| Redis / 消息队列 | 当前量级用不上；云函数 + 定时触发器已覆盖异步需求 |
| 自建 WebSocket | 私信实时性可放宽到秒级，云数据库 watch 足够，不值得买服务器 |
| 微信支付 / 任何支付 SDK | 产品明确不碰资金（PRD 8.1、9.2） |
| 第三方分析 SDK | 需传数据出境，GDPR 风险，自建埋点在此规模下成本更低 |
| 状态管理库 | 小程序原生的页面数据 + 全局 `app.globalData` 够用 |
| AI 绘图模型 | 小红书封面用模板套图，图像生成是成本大头且收益不明确 |
| Docker / K8s | 无自建服务器，无部署编排需求 |

## 14. 技术风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 订阅消息授权率过低 | L2 自动分发触达率被封顶，即时响应链路失效 | 埋点持续观察；在三个正反馈时刻顺势请求授权；授权率长期低于 40% 则考虑把即时响应降级为"进小程序才看到" |
| 云开发免费额度耗尽 | 服务中断 | 监控用量；`aiGateway` 记账；预聚合减少查询；必要时开启按量付费（月成本预算 200 元内，见 PRD 8.3） |
| 云开发生态绑定 | 未来扩端需重写后端 | handler / service / dao 三层分离，业务逻辑不下沉到数据库查询 |
| 体验版成员数上限 | 真实运营规模受限 | 需在开发前核实当期规则（PRD 附录 C 第 2 项）；据此设定伦敦冷启动的用户规模目标 |
| AI 输出不稳定 | 发布链路被阻断 | JSON Schema 校验 + 重试 1 次 + 降级为普通表单，AI 永不成为必经路径 |
| 单人开发的知识断点 | 停更后无法维护 | 状态机、枚举、额度配置集中且有测试；README 与本文档记录选型理由而非仅记录结论 |
