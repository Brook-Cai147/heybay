02

V1.0「同路人」→ V2.0「喊呗」

V1.0 建了一个内容社区的容器，却期待它自己长出撮合与交易。V2.0 的工作重心不是加功能，而是补上那条主干。

V1.0 同路人

  • 海外旅行搭子社区
  • 原子单位是帖子，发完就没人知道后来发生了什么
  • 城市社区只是内容分区
  • 口号写了「轻量化担保交易」，功能为零
  • 信任 = 一个「已认证」标签 + 举报
  • 先审后发，海外时差下即时需求全部失效
  • 发了没人理 → 用户当天流失，无兜底
  • 11 个页面纯前端，无后端
把需求结构化把审核放快把流量收拢到城市密度不足时用 AI 兜住

V2.0 喊呗 HeyBay

  • 海外旅行场景下的异地求助撮合平台
  • 原子单位是需求单：可被接、可闭环、可评价、可度量
  • 城市 = 供给容器，当地先有人入驻才有能力承接需求
  • 明确不碰资金：托管「约定单」而不是托管钱
  • 四层信任 + 双向评价 + 四档徽章与证据清单
  • 分级审核：信任分 ≥30 先发后审，机审毫秒级
  • 小螺作为供给的兜底层，无人响应时先把需求兜住
  • 小程序 + 云开发全栈：7 云函数 / 10 集合 / 事务写入

被修正与被移除的 V1.0 设计

微信支付（原标注"后续迭代"）

明确移除。跨境结算需企业资质与外汇备案，形成预付资金池涉及无证经营支付业务的法律风险。改为线下结算 + 约定单。

「同步小红书」

重定义为「生成小红书图文」。小红书没有开放给第三方的发布 API，市面宣称一键同步的实质都是生成文案 + 存图 + 手动发布。写清技术不可行，比留一个做不出来的需求更负责。

签到送积分

重定义为增信任务体系。原积分体系有 banner 无设计，获取、消耗、价值锚定全部缺失。现在完成任务得到的是曝光加成与信任分进度。

「本地居民」作为供给端

移除。非华人本地居民既不用微信也不读中文界面。供给端明确为当地华人、留学生、长期旅居者。

首页与「组圈」职责重叠

拆开。首页 = 需求广场，城市 Tab = 社区与供给池。三处搜索框合并为一个统一搜索页，四个 Tab 范围一致。

用户无节制自建小组

加上健康度与数量上限。建组上限 = 城市周活跃用户数 ÷ 20，伦敦初期就是 0~2 个。冷启动期不允许提前把流量碎片化。

长期明确不做（写入产品原则，用于抵御功能蔓延）

  1. 交友与约会属性——一旦擦边交友进入，真实求助需求会被淹没，供给端流失，生态不可逆地变差。性别字段只能用于「仅同性响应」，不提供「仅异性响应」选项，从数据结构层面消灭擦边需求。
  2. 平台代收资金——长期结论，不是阶段性妥协。
  3. AI 全自动代替用户与真人协商（L3）——责任无法归属，AI 承诺会造成真实损失。
  4. 采集身份证件影像——GDPR 下一次泄露的后果远大于产品收益。
03

核心机制

撮合是一个密度游戏：单位时间、单位城市内，必须有足够多的「可被响应的具体需求」和「愿意响应的在地供给」相遇。

需求单状态机

草稿发布 招募中有人响应 待选定选定 已确定双方确认 已完成互评 已评价
已过期预约型在期望时间后 24h、即时型按有效时长自动过期 → 归档进城市知识库
已取消任一方取消（记录取消方） 撤销选定退回「待选定」重新挑人，原有响应全部保留 已下架违规

需求单必然会终结

不存在永久挂着的需求。这一条直接解决 V1.0 的死水内容堆积——社区里永远只陈列「还有效的事」。

过期不等于浪费

过期需求单连同响应内容进入城市知识库，成为小螺的检索语料。稀疏期的失败也在积累资产。

取消不重罚

信任分主要看双方真实互评。按取消次数扣分是在惩罚正常行为，还会诱导用户不点取消、把单子挂到过期——那是更坏的结果。

它替代了 V1.0 的「担保交易」。发生纠纷时，约定单 + 聊天记录 + 评价构成判定依据，处理结果体现为信任分与封禁，而非退款。

这套「信誉担保」提供了资金担保约 80% 的信任价值，而风险与合规成本接近于零。数据结构（约定单、金额字段、状态机）同时为将来真正的担保交易预留了升级空间。

平台托管的是共识与凭证，不是钱。

反死水：五个层面同时施压

需求层强制时效 + 自动过期
分发层精准推送 + 小组广播 + 二次改写投放
容器层小组健康度 + 建组上限，强制流量收拢
兜底层无人响应时 AI 直接作答，挽回流失
运营层每日城市话题 + 每周精华 + 学校 BD

配套内容播种：伦敦上线前预置 30 条社区内容 + 100 条问答语料。冷启动期的社区可以是人工的，但不能是空的。

开城标准：四项同时达标才复制下一城

≥50认证本地响应者
≥30周需求单
≥60%需求单首响率
≥40%响应者次月留存

个人开发者的运营带宽只够一座城；3 城试点等于把密度除以 3。冷启动渠道用学校（UCL/KCL/IC/LSE），产品结构用城市——旅行者只知道城市不知道学校。

04

AI 设计：小螺

在喊呗里，AI 不是效率工具，AI 是供给的兜底层。

推导过程：最致命的流失点不是「匹配不精准」，而是「发了需求没人理，用户当天就走了」——旅行者在当地只停留几天，这类流失不可挽回。冷启动期供给必然稀疏，运营短期解决不了。所以 AI 的第一价值不是提效，而是在真人供给缺席时先把这个用户的需求兜住。

兜底而非替代

真人响应永远优先展示，AI 答案只在无响应或用户主动询问时出现，且明确标注来源。

从模糊到结构化

AI 承担翻译工作，用户不需要学会填表——这是把需求方门槛降到最低的唯一办法。

自主性由用户选

而不是由产品单方决定。默认最保守档，用户按信任程度自行上调，随时可回退。

自主性阶梯：把「该不该自动」变成可调节的产品维度

全自动有风险、纯手动没价值。正确答案不是在两者之间取折中点，而是把自主性本身产品化为一个可解释、可调节、可回退的档位。

L0只读建议

解析需求、给攻略与清单、答疑。不对外发送任何内容。

新用户前 3 单
L1一键代发

生成邀请文案 + 候选人名单，等你勾选后统一发出。不自动发送。

全局默认档
L2自动分发

自动向匹配响应者推送结构化需求卡片；2h 无响应自动改写文案二次投放（≤2 次）。不进 1v1 私信、不模拟真人语气。

用户手动开启
L3自动协商

本产品永不实现，并把理由展示给用户：责任无法归属、AI 承诺会造成真实损失、身份不明示已属需披露行为、个人开发者无力承担纠纷成本。

不提供

L1 → L2 的引导不藏在设置页里等用户发现，而是在「L1 发送邀请后获得响应」这个正反馈时刻提示：在信任已建立的时刻请求更多授权。

护栏与红线

四类字段禁止代填

金额、见面时间、见面地点、联系方式。AI 只能留空，必须由人填写。Schema、规范化层、发布校验三道防线。

事实性边界

签证、医疗、法律、移民问题在服务端前置拦截——不调模型、不占额度，直接给官方链接。

身份明示

一切对外内容强制带「AI 协助」标识；L2 分发只能是系统卡片而非聊天气泡，强制带「由小螺代为分发」。

来源标注

兜底答案必须标注来源：「根据伦敦小组 3 条历史回答，请自行核实」。

可解释性

每条推荐必须给出依据字段，不允许「猜你喜欢」式无理由推荐。名单由代码排序，理由由模型写，理由里的每个数字都必须能追溯回依据字段。

频控与可回退

同一响应者每日被触达 ≤3 次，被拒 2 次进 7 天冷却；任何 AI 生成内容可一键改手动，L2 可随时关闭且立即生效。

离线评测：没有用户也能证明 AI 质量

四类禁填字段误填0 次红线

依赖真实流量的三项指标（发布转化率 +20%、首响率 +30%、打扰投诉率 ≤2%）在没有真实用户前无法验证，因此推后到 M5，不在当前阶段假装已达成。

当前阶段改用离线评测集：npm run eval:parse 输出三个数与逐条 diff。这一项不需要任何用户即可度量。

评测抓出的真问题：Prompt 要求「归不进 8 类就留空」，而 Schema 把 category 设成必填——擦边交友因此被硬塞进「搭子同行」，正撞产品红线。两条擦边用例把它抓了出来。

05

信任与安全

这是一个促成陌生人在异国线下见面的产品，安全是核心差异化而非附加项，因此定为 P0 并写入产品定位。

四层信任，全部零资质门槛，全程不收证件

L1基础身份

微信授权登录 + 常驻城市自选 + 性别自填（可留空）

可信度 低
L2自证

.edu 邮箱验证码（只存「已验证 + 学校名」）· 社媒绑定 · 自我介绍完整度

可信度 中
L3履约

真实完成单数 · 双向评价 · 平均响应时长 · 被举报率

可信度 高
L4社区背书

组长/老用户背书，每月限 2 次，被背书者违规则背书人连带扣分

可信度 高

为什么不收证件

护照、签证、学生证属身份证件类敏感个人信息。GDPR 下处理这类数据需要合法性基础、数据保护影响评估、加密存储与最小化留存——个人开发者不具备承担这一责任的能力。V2.0 完全不采集证件影像。

不显示裸分数

信任分 0~100 内部计算，对外只显示四档徽章 + 可展开的证据清单：「已完成 12 单｜好评率 100%｜平均 18 分钟响应｜UCL 邮箱已验证」。让用户看到「他凭什么可信」，而不是一个不可解释的数字。

注册零门槛，只在三处拦截

① 接付费地陪 / 翻译类单 → L2 + 信任分 ≥40；② 发或接住宿类单 → L2 + 至少 1 条好评；③ 首次发起线下见面确认 → 强制阅读安全提示。其余全程不拦。

用收益框架而非恐惧框架

增信引导不说「为了安全请认证」（暗示危险），而说「补全后被选中的概率高 2.6 倍」，并让高信任分用户在响应列表天然靠前——让增信的动机来自竞争。

不采集手机号

微信手机号快速验证接口对个人主体不开放；自建短信通道面向海外号码成本与合规都不划算。云函数拿到的 openid 本身就是微信校验过的可信身份，手机号不额外提供可信度。

不存紧急联系人

行程报备走微信自带分享把行程卡片发给朋友或群，不在后台存储第三方联系人字段——零成本、零合规负担，效果等同。

安全机制：事前 / 事中 / 事后

事前

  • 仅同性响应开关（默认关闭，女性首次发单时主动提示）
  • 地点只到街区 / 地铁站级，疑似门牌地址提示拦截
  • 选定后强制展示一次安全提示卡
  • 住宿类要求双方均 L2 + 独立安全须知

事中

  • 行程报备：一键生成卡片经微信分享给朋友
  • 一键 SOS：英国 999 / 欧盟 112 / 美国 911 + 使领馆
  • 反诈提示：出现「先转账」「押金」「退出平台交易」等模式时向双方弹出，避免误伤正常沟通

事后

  • 双向评价，互评前互不可见；7 天未评视为默认好评但不计入好评率
  • 拉黑后互相不可见、不可响应、不可私信
  • 六类举报，人身安全类直接冻结接单能力
  • 处罚阶梯：提示 → 限流 → 禁接单 7 天 → 永久封禁

联系方式交换：全站只有一个下发点

联系方式由用户在「我的」里自填，发布需求时不需要、也不允许挂在需求单上——那等于向全城公开个人账号。只在需求单进入「已确定」之后、在需求方与被选定的响应者之间双向下发；广场、列表、卡片一律不含。用户可随时清空，但已经看到的收不回，界面如实说明这一点。

反擦边交友治理：从数据结构层面消灭

① 品类白名单只有 8 类，没有「交友」「同城」「聊天」选项，归不进 8 类的需求无法发布。② 语义拦截覆盖变体、谐音、拼音缩写。③ 偏好字段单向可用，只有「仅同性响应」，不提供「仅异性响应」。④ 举报独立分类，优先级仅次于人身安全。⑤ 处罚从重，跳过提示直接禁接单 7 天，二次永久封禁。

社区规范首屏：喊呗解决的是「办事」，不是「处对象」。让规则以产品价值观的方式表达，比藏在协议里有效。

06

指标与商业化

北极星指标 每周成功撮合数

需求单被接 + 双方确认完成。同时依赖供需两侧，无法靠单侧刷量做高。

护栏 1 需求单首响率 ≥60%

发布后 2h 内至少 1 条响应。它是撮合数的领先指标，能在撮合完成前就暴露密度问题。

护栏 2 响应者次月留存 ≥40%

需求方是流动的（旅行者用完即走），供给方才是留存的根基。供给一旦流失，产品立刻回到死水状态。

明确不作为核心指标 DAU · 发帖量 · 小组数

V1.0 的看板以这三项为主。它们都能靠「看内容」刷出来，与撮合成功无因果关系。

核心漏斗

浏览 → 发布≥25%
发布 → 首响≥60%
有响应 → 选定≥80%
选定 → 完成≥70%
完成 → 评价≥60%
30 天二次发单≥20%

四阶段商业化：前置结论是不碰资金

阶段 0验证期（0~6 个月）不赚钱

唯一目标是把伦敦的每周成功撮合数跑起来。任何收费都会在密度不足时杀死冷启动。

阶段 1会员订阅 ¥18/月

向需求方卖「更快被响应、更容易被选中」：置顶曝光、在架上限 3→10、完整信用档案、高级筛选、AI 高成本能力放开。

阶段 2供给端变现

认证徽章年费、接单曝光包、个人服务主页（做本地向导 IP）。供给端有真实收益动机，付费意愿显著高于旅行者。

阶段 3本地商家与生态

城市入驻位、内容推广位、留学生活服务 CPA 分成。收入天花板最高且完全不碰资金。

阶段 4担保交易（条件成熟才做）

需企业主体、支付资质、专职客服与风控。个人开发者阶段明确不做，但数据结构已预留升级空间。

定价原则：不给「AI 调用次数」定价，给「结果」定价

会员权益的对外表述是「更快被人响应、更容易被选中」，AI 额度只是实现手段，不作为卖点陈列。一旦让用户按次数计算 AI 成本，付费意愿会立刻崩塌，而且会把产品价值锚定在「AI 工具」而非「撮合服务」上。

成本侧：短文本能力完全给得起免费（日活 500 量级月 AI 成本几十元）。真正贵的是长输出和图像生成——因此小红书图文只做模板套图不做 AI 绘图，行程生成设每日限额。月运营成本可控制在 200 元以内，达到阶段 1 后单城即可覆盖成本。

明确的技术不可行项（写进文档避免返工）

小红书内容同步

无开放发布 API，只能生成内容 + 复制 + 引导手动发布。

跳转外部 App

小程序无法一键打开小红书，只能复制到剪贴板。

无授权主动推送

只能依赖订阅消息，一次授权对应一条推送，因此 L2 分发的触达率上限受授权率约束。

境外精准定位

精度与授权率均低于国内，城市采用「自动定位 + 手动选择」双轨，且所有逻辑以手动选择为准。

向量库

冷启动期语料只有几百条，向量检索的质量提升观察不到，却多一个必须维护同步的组件。起步用关键词 + 标签过滤，升级条件：单城语料 >2000 条或兜底采纳率 <50%。

独立 Web 后台

运营后台做成小程序内的管理员页面（openid 白名单 + 云函数二次校验），只做四件事：待审、举报、用户、看板。

最大的落地障碍：个人主体拿不到 UGC 类目

小程序涉及发帖、评论、私聊等 UGC 功能需要「社交-社区/论坛」类目，而该类目不向个人主体开放，后台入口为灰态。这个优先级高于任何功能设计。

解法是 A + B 双 Demo：Demo A 完整前后端 + 数据库，以微信小程序体验版发布——体验版无需提交审核即可分享给受邀成员，不受类目限制，是零成本、零合规风险又能拿到真实用户数据的唯一路径，且天然适配「伦敦单城小范围运营」；Demo B 是升级路径原型，演示具备主体与资质后的形态（担保交易、商家入驻、多城联动），明确标注为 Roadmap 演示。

升级触发条件：伦敦跑到阶段 1 的收入验证，再启动主体注册 → ICP 备案 → 类目申请 → 正式发布。届时 Demo A 的代码与数据可直接迁移。
