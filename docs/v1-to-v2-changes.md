# 从「同路人」到「喊呗 HeyBay」：V1.0 → V2.0 版本变动说明

> 可对外分享版本。撰写日期 2026-09-04。
> 完整需求定义见 `docs/prd-heybay-v2.md`；内部实施口径见 `memory-bank/design-document.md`。

---

## 一句话总结

**V1.0 建了一个内容社区的容器，却期待它自己长出撮合与交易；V2.0 把产品的原子单位从「帖子」换成「需求单」，并补上了让这个单子必然终结、必然被度量的那条主干。**

| | V1.0 同路人 | V2.0 喊呗 HeyBay |
|---|---|---|
| 定位 | 海外旅行搭子社区 | 海外旅行场景下的异地求助撮合平台 |
| Slogan | 无 | 在国外，喊一声就有人 |
| 原子单位 | 帖子（内容） | 需求单 Request（可被接、可闭环、可评价） |
| 城市社区的角色 | 内容分区 | 供给容器：当地先有人入驻，才有能力承接需求 |
| 交易 | 口号写了「轻量化担保交易」，功能为零 | 明确不碰资金：托管「约定单」而不是托管钱 |
| 信任 | 身份标签 + 举报 | 四层信任体系 + 双向评价 + 信任分四档徽章 |
| 冷启动兜底 | 无（发了没人理就流失） | AI 助手「小螺」作为供给的兜底层 |
| 工程形态 | 11 个页面 + 自定义 tabBar，**无后端** | 小程序 + 微信云开发：7 个云函数、10 个集合、状态机全走事务 |

---

## 二、变动的来源：V1.0 复盘出的 14 个问题

V2.0 的每一条设计改动都对应下面某一条，不是凭感觉加功能。

**S 级（阻断产品成立）**

1. **交易闭环缺位** —— 定位写明「免费拼搭子 + 付费租搭子 + 旅行轻交易 + 轻量化担保」，功能结构里却没有服务发布、订单、支付、评价任何一个模块，「我的订单」只是个预留入口。
2. **没有匹配机制** —— 「搭子出行」只是帖子的一个分区标签，没有结构化字段、没有接单动作、没有状态流转。用户发完帖，产品不知道后来发生了什么，也无法衡量成功。
3. **主体资质导致无法上线** —— 个人主体微信小程序拿不到「社交-社区/论坛」类目，UGC 发帖、评论、私信是硬性禁区，而 V1.0 的全部核心功能都落在这个禁区里。

**A 级（直接导致社群死水）**

4. **先审后发** —— 海外用户与国内审核有时差，一条内容延迟数小时才可见，「今天拼饭」「现在应急」这类即时需求全部失效。这是社群死水最被低估的成因：不是用户不发，是发了看不见、看见了已过期。
5. **反死水规则过于单薄** —— 只有「7 天无互动降权 + 小组需有主题内容 + 用户可自建小组」三条。
6. **用户自建小组无节制** —— 把有限流量碎片化成一堆死水小组。
7. **无兜底** —— 需求无人响应用户直接流失，且旅行者在当地只停留几天，这类流失不可挽回。

**B 级（体验与信任缺陷）**

8. 认证只有结果没有过程：写着「已认证显示」，但没定义认证依据、材料、审核方式与展示分级。
9. 安全体系缺失：只有帖子举报，没有拉黑、双向评价、信用记录、线下见面安全机制。
10. 首页与「组圈」职责重叠，两个 Tab 做同一件事，且命名在导图与高保真图之间不统一。
11. 三处搜索框可搜范围各不相同，且「地陪」「二手」是交易品类却没有交易功能承接。
12. 积分体系有界面无设计：高保真图有「签到送积分」banner，获取、消耗、价值锚定全部缺失。

**C 级（可行性与预期问题）**

13. **「同步小红书」不可实现** —— 小红书没有开放给第三方的内容发布 API，市面上宣称「一键同步」的实质都是生成文案 + 批量存图 + 引导手动发布；走私有接口违反平台协议且会封号。
14. **「本地居民」作为供给端不成立** —— 非华人本地居民既不用微信也不读中文界面。

## 三、V2.0 的四个动作

把 14 条收敛成设计动作，就是四件事：**把需求结构化、把审核放快、把流量收拢到城市、在密度不足时用 AI 兜住。**

### 1. 需求结构化：需求单取代帖子

需求单有 13 个字段（品类 / 城市 / 标题 / 详情 / 时效类型 / 期望时间 / 地点范围 / 报酬类型 / 参考金额 / 人数 / 偏好 / 可见范围），和一条完整的状态机：

```
草稿 → 招募中 → 待选定 → 已确定 → 已完成 → 已评价
                    ↑         ├→ 撤销选定（退回待选定，响应全部保留）
                    │         └→ 已取消（记录取消方）
                    └→ 超时无选定 → 已过期 → 归档进城市知识库
```

三条关键规则：

- **需求单必然会终结**。预约型在期望时间后 24h 过期，即时型按有效时长过期。这一条直接解决 V1.0 的死水内容堆积。
- **过期不等于浪费**。过期需求单连同响应内容进入城市知识库，成为 AI 兜底作答的语料。稀疏期的失败也在积累资产。
- **同城同时在架上限**：免费 3 条、会员 10 条，防刷屏。

品类由 V1.0 的四大帖子主题升级为 **8 类白名单**：搭子同行 / 付费地陪 / 借物易物 / 住宿 / 打听咨询 / 代购跑腿 / 翻译陪同 / 应急求助。**白名单里没有「交友」「同城」「聊天」——归不进 8 类的需求无法发布**，这是从数据结构层面消灭擦边需求。

### 2. 审核放快：分级审核取代先审后发

| 分级 | 策略 |
|---|---|
| 新用户前 3 条 / 信任分 <30 | 机审 + 人工复核后可见（目标 30 分钟内） |
| 信任分 ≥30 且无违规 | 机审通过即可见，**先发后审** |
| 敏感品类（住宿 / 应急 / 含金额的付费单） | 机审 + 人工抽检 |
| 命中高风险语义 | 直接拦截，给出可修改提示 |

机审毫秒级，由 AI 承担；人工复核目标每天 <20 分钟。

### 3. 流量收拢：城市是唯一一级容器

- 城市（官方维护）→ 官方 5 分区（找搭子 / 问本地 / 跑腿代购 / 闲置转让 / 住宿）→ 兴趣小组（受约束）
- **小组健康度**取代「7 天无互动降权」：周度算分，60 分以上正常，30~60 降权，连续 3 周 <30 归档合并。
- **建组数量上限** = 该城市周活跃用户数 ÷ 20。伦敦初期就是 0~2 个——这是有意的克制，冷启动期不允许提前碎片化。
- **开城标准**：认证响应者 ≥50 人、周需求单 ≥30 条、首响率 ≥60%、响应者次月留存 ≥40%，四项同时达标才开下一城。撮合是密度游戏，3 城试点等于把密度除以 3。
- 冷启动**渠道**用学校（UCL/KCL/IC/LSE），产品**结构**用城市。V1.0 的困惑源于把渠道和结构混为一谈。

### 4. AI 兜底：小螺

**AI 不是效率工具，AI 是供给的兜底层。** 推导过程：本产品最致命的流失点不是「匹配不精准」，而是「发了没人理，用户当天就走了」，而冷启动期供给必然稀疏，这不是运营短期能解决的。

- 14 项 Agent 工具（解析、建单、语料检索、可解释匹配、邀请文案、分发、落地清单、机审、反诈提示、小红书图文、应急卡、城市话题、评价聚合、翻译）
- **自主性阶梯 L0/L1/L2**，默认 L1，用户自己往上调；**L3 自动协商明确永不实现**，并把理由展示给用户
- **四类字段 AI 一律不代填**：金额、见面时间、见面地点、联系方式
- 事实性边界：签证 / 医疗 / 法律 / 移民**在服务端前置拦截**，不调模型
- 兜底答案强制标注来源（"根据伦敦小组 3 条历史回答，请自行核实"）

## 四、被明确修正与移除的 V1.0 设计

| V1.0 | V2.0 处置 |
|---|---|
| 先审后发 | **改为分级审核** |
| 微信支付（标注"后续迭代"） | **明确移除**，改为线下结算 + 约定单 |
| 「担保交易」 | 替换为**信誉担保**：托管约定单、沉淀双向评价、留存纠纷证据，处理结果是信任分与封禁而非退款 |
| 同步小红书 | **重定义**为「生成小红书图文」，不承诺自动发布 |
| 「本地居民」作为供给端 | **移除**，供给端明确为华语人群 |
| 签到送积分 | 重定义为**增信任务体系**：得到的不是积分，而是曝光加成与信任分进度。原积分体系因缺少价值锚定而废弃 |
| 首页与组圈重叠 | 首页 = 需求广场，城市 Tab = 社区与供给池，去掉重复推荐流 |
| 三处搜索范围不一 | 统一搜索页，四个 Tab（需求单/内容/用户/小组），范围一致 |
| 身份标签「已认证显示」 | 升级为四层信任 + 四档徽章 + 证据清单 |
| 热搜榜 | 保留，冷启动期改为「本周伦敦大家在问什么」，由真实需求单聚合，避免无数据暴露冷清 |
| 我的订单（预留入口） | 落地为「我的需求单 / 我的接单」，含状态分组 |
| 简易 B 端后台 | 收窄为四件事：待审队列、举报队列、用户管理、数据看板 |

### 新增的「长期明确不做」

写进产品原则，作为后续需求评审时抵御功能蔓延的依据：

1. **交友与约会属性** —— 不做异性筛选、不做颜值展示、不做随机匹配。一旦擦边交友进入，真实求助需求会被淹没，供给端流失，生态不可逆地变差。性别字段只能用于「仅同性响应」这一个安全用途，**不提供「仅异性响应」选项**。
2. **平台代收资金** —— 跨境结算需企业资质与外汇备案，形成预付资金池涉及无证经营支付业务的法律风险。这是长期结论，不是阶段性妥协。
3. **AI 全自动代替用户与真人协商** —— 责任无法归属、AI 承诺会造成真实损失、身份不明示在多数地区已属需披露行为。
4. **收集身份证件原件** —— GDPR 下处理证件类敏感信息需要合规能力，个人开发者不具备，一次泄露的后果远大于产品收益。

## 五、信任与安全：从「一个标签」到一整套

**四层信任，可累加，全部零资质门槛，全程不收证件。**

| 层 | 内容 | 可信度 |
|---|---|---|
| L1 基础身份 | 微信授权登录 + 常驻城市自选 + 性别自填（可留空） | 低 |
| L2 自证 | `.edu` 邮箱验证码（只存"已验证 + 学校名"）/ 社媒绑定 / 自我介绍完整度 | 中 |
| L3 履约 | 真实完成单数、双向评价、平均响应时长、被举报率 | **高** |
| L4 社区背书 | 组长/老用户背书，每人每月限 2 次，被背书者违规则背书人连带扣分 | 高 |

两个关键取舍：

- **不显示裸分数**，显示四档徽章（新面孔 / 靠谱 / 老手 / 城市之光）+ 可展开的证据清单（"已完成 12 单｜好评率 100%｜平均 18 分钟响应｜UCL 邮箱已验证"）。让用户看到「他凭什么可信」，而不是一个不可解释的数字。
- **注册零门槛，强制校验只在三处发生**：接付费地陪/翻译类单、发或接住宿类单、首次发起线下见面确认。其余全程不拦。
- 增信引导用收益框架（"补全后被选中的概率高 2.6 倍"）而不是安全框架（"为了安全请认证"）——后者在暗示危险。

**安全体系（P0，不是附加项）**：事前有仅同性响应开关、地点模糊到街区级、安全提示卡、住宿类特殊规则；事中有行程报备（走微信分享，不在后台存第三方联系人）、一键 SOS、私信反诈提示；事后有双向评价、拉黑、六类举报、四级处罚阶梯。

**联系方式交换**只在需求单进入「已确定」之后、只在需求方与被选定的响应者之间双向下发。广场、列表、卡片一律不含。用户可随时清空，但已经看到的收不回——界面如实说明这一点。

## 六、商业化：从未定义到四阶段

前置结论：**平台不代收、不代付、不托管任何资金。**

- **阶段 0 验证期（0~6 个月）**：不赚钱。任何收费都会在密度不足时杀死冷启动。
- **阶段 1 会员订阅**：向需求方卖「更快被响应、更容易被选中」，¥18/月 或 ¥88/年。
- **阶段 2 供给端变现**：认证徽章年费、接单曝光包、个人服务主页。供给端有真实收益动机，付费意愿高于旅行者。
- **阶段 3 本地商家与生态**：城市入驻位、内容推广位、留学生活服务 CPA 分成。收入天花板最高且完全不碰资金。
- **阶段 4 担保交易**：需企业主体与支付资质，个人开发者阶段明确不做，但数据结构（约定单、金额字段、状态机）预留了升级空间。

**定价原则：不给「AI 调用次数」定价，给「结果」定价。** 一旦让用户按次数计算 AI 成本，付费意愿会立刻崩塌，而且会把产品价值锚定在「AI 工具」而非「撮合服务」上。

单位经济：月运营成本可控制在 200 元以内（云开发 + AI token + 域名），达到阶段 1 后单城即可覆盖成本。

## 七、指标体系：换掉了虚荣指标

- **北极星**：每周成功撮合数（需求单被接 + 双方确认完成）。同时依赖供需两侧，无法靠单侧刷量做高。
- **护栏 1**：需求单首响率（发布后 2h 内至少 1 条响应），目标 ≥60%。它是撮合数的领先指标。
- **护栏 2**：本地响应者次月留存，目标 ≥40%。需求方是流动的（旅行者用完即走），供给方才是留存的根基。
- **明确不作为核心指标**：DAU、发帖量、小组数量。V1.0 的数据看板以这三项为主，它们都能靠「看内容」刷出来，与撮合成功无因果关系。

## 八、工程侧的实际变化

V1.0 是 11 个页面的纯前端；V2.0 是有服务端边界的完整应用。

- **7 个云函数**：`login`（登录建档）、`requestFlow`（发布/取消/完成）、`responseFlow`（响应/选定/撤销）、`aiGateway`（全项目唯一模型出口）、`moderation`（三层内容安全）、`track`（埋点）、`cron`（过期扫描等定时任务）
- **10 个集合**，数据库权限收成「所有用户不可读写」——端侧读写全部被拒，一切数据访问只能走云函数
- **状态变更一律走事务**，状态与审计日志同生共死
- **`aiGateway` 8 步编排**：额度 → 缓存 → 组 Prompt → 调模型 → 校验 → 重试一次 → 降级 → 记账。能力由注册表驱动，加一项能力是加一行而不是加一个 `if`
- **只讲 OpenAI 兼容协议**：换供应商等于改三个环境变量，厂商专有字段走 `AI_EXTRA_BODY`，代码不绑任何一家
- **AI 离线评测**：36 条黄金标注 + 评测脚本，首轮基线**字段抽取准确率 89.2%、四类禁填字段误填 0 次**（达标线 85%）

### 落地形态：A + B 双 Demo

个人主体拿不到 UGC 类目这条硬约束绕不过去，所以：

- **Demo A（主线）**：完整前后端 + 数据库，P0 功能真实可用，AI 接真实模型。发布形态是**微信小程序体验版**——无需提交审核即可分享给受邀成员，因此不受个人主体类目限制。这是零成本、零合规风险、又能拿到真实用户数据的唯一路径。
- **Demo B**：升级路径演示原型，演示「如果具备主体与资质，产品会长成什么样」（担保交易、商家入驻、多城联动），明确标注为 Roadmap 演示。

**升级触发条件**：伦敦跑到阶段 1 的收入验证，再启动主体注册 → ICP 备案 → 类目申请 → 正式发布。届时 Demo A 的代码与数据可直接迁移。
