## 1. 产品定位

### 1.1 一句话定位

**在国外，喊一声就有人。** 喊呗面向海外旅行者与当地华人/留学生：旅行者把落地后的具体需求喊出来，当地人顺路接下来。

英文 Slogan：Holler once, someone's already there.
副 Slogan（供给端）：顺路帮个忙，也是一份收入。

### 1.2 品牌

- 中文名喊呗、英文名 HeyBay、AI 助手小螺、仓库名 `heybay`，四者构成一套，全渠道统一使用。
- 选「喊呗」的决定性理由是**零教育成本 + 可动词化**：「上喊呗喊一个」——品牌名本身就是行为召唤。对一个零预算、靠自然口碑传播的项目，这比听感优雅重要得多。
- 「海螺」不作产品名（语义不直白、无法动词化、搜索被海螺水泥/海螺沟占据），但下沉为品牌资产：AI 助手命名「小螺」、吉祥物、以及「航海时代靠螺号在陌生海岸互相呼应」的品牌故事。

### 1.3 业务边界

**做**：欧美城市（首发伦敦）、华语用户、旅行相关的求助与轻服务、微信生态内全流程、信誉担保。

**不做（本期）**：国内同城场景、非旅行品类交易、资金代收代付与提现、复杂清结算、跨境物流。

**长期明确不做（写入产品原则）**：

1. **交友与约会属性**。一旦擦边交友进入，真实求助需求会被淹没，供给端流失，生态不可逆地变差。
2. **平台代收资金**。理由见第 10 章。
3. **AI 全自动代替用户与真人协商**。理由见 6.3。
4. **收集身份证件原件**。理由见 5.5。

## 2. 问题定义

### 2.1 核心矛盾

撮合是一个**密度游戏**：单位时间、单位城市内，必须有足够多的「可被响应的具体需求」和「愿意响应的在地供给」相遇。

V1.0 的每一个设计选择都在降低这个密度——非结构化的帖子降低可匹配性，先审后发降低时效，无节制建组切碎流量，无兜底让稀疏期的用户直接流失。

V2.0 的全部工作可以概括为四件事：**把需求结构化、把审核放快、把流量收拢到城市、在密度不足时用 AI 兜住。**

### 2.2 竞品与差异化

| 竞品 | 用户当前如何解决 | 缺口 |
|---|---|---|
| 小红书 | 发帖找搭子、看攻略 | 无撮合闭环、无身份可信度、私信转化极低、无法按城市沉淀在地供给 |
| 微信群（华人群/校友群） | 群里喊一句 | 信息瞬时淹没、无信用记录、无法搜索历史、进群门槛 |
| Meetup / Couchsurfing | 参加活动、找沙发主 | 英文环境、以活动而非需求为单位、华人使用率低 |
| 马蜂窝/穷游/当地玩乐 | 买标准化地陪、一日游 | 商品化预制产品，无法承接临时的、具体的、非标的小需求 |
| 闲鱼 / 华人生活网 | 二手、租房、跑腿 | 定居者视角，无旅行时效性，无移动端撮合 |
| 私域地陪中介 | 微信中介推荐 | 不透明、抽成高、无评价、纠纷无处理 |

**差异化交叉点**：以「具体需求 + 时效」为单位（区别于内容与活动平台），以「在地华语社区」为供给池（区别于标准化商品平台），以「信誉担保而非资金担保」建立信任（区别于中介与交易平台），以「AI 兜底」解决冷启动稀疏（所有竞品都没有）。

一句话：**闲鱼的「求购」逻辑 + 小红书的社区语境 + 旅行的时效性，跑在微信里。**

## 3. 用户与场景

### 3.1 三类角色

角色**不是注册时的固定身份，而是可切换的行为状态**。同一个留学生今天是响应者，下个月去别的城市旅行就是需求方。因此产品是**单一账号 + 双向能力**，而不是分供给端/需求端两类用户。

1. **需求方（喊人的）**：短期到访欧美的中国旅行者，也含当地留学生。需求具体、时效强、停留期短、决策快、信任基础薄。
2. **本地响应者（接活的）**：当地常驻华人、留学生、长期旅居者。有在地信息与碎片时间，动机是赚钱、攒信用、社交，但**耐心有限**——被无效需求打扰两三次就会永久关闭通知。
3. **泛参与者**：其他旅行者与短期访客。

**设计含义**：产品对两侧的容忍度**故意不对称**。需求方的门槛必须极低（低到一句话就能发出需求），响应者的打扰必须被严格控制（频控、精准分发、可关闭）。V1.0 对两侧一视同仁，是隐藏的供给流失源。

### 3.2 用户画像

- **林悦，26 岁，需求方**。上海互联网公司运营，年假 10 天独游伦敦+爱丁堡。会用小红书做攻略但不敢私信陌生人。她不缺钱，缺的是「当地有个人能问一句」。决策逻辑：只要看起来靠谱、代价不高，就愿意试。
- **陈默，23 岁，本地响应者**。UCL 研一，伦敦第二年，生活费紧张，会拍照、熟悉交通、周末有闲。痛点是正规兼职受签证工时限制、校友群里的接单信息很快被淹没、遇到过临时放鸽子和压价。决策逻辑：单子要值当、人要靠谱、流程别麻烦。
- **苏姐，38 岁，长期旅居者**。巴黎八年，做代购和自媒体，是社区里的信息节点。决策逻辑：图长期 IP 与客源沉淀，不图单次收入。城市组长的最佳人选。

### 3.3 核心场景

按**时效类型**分两类，这是 V2.0 新增的关键区分维度：

**预约型（有明确未来日期）**

- S1 行前一周：发「9/12 上午想找人一起逛大英博物馆，中文，女生优先」→ 有人接单 → 私信约地点 → 完成 → 互评
- S2 行前三天：找付费地陪一日游含拍照，预算 £80 → 3 人响应 → 看信任档案选一个 → 生成约定单，线下结算
- S3 行前：找短期住宿 / 行李寄存 / 借转换插头

**即时型（当天或数小时内，需要主动分发）**

- S4 落地当天：「现在在国王十字，附近哪里能买到电话卡？」→ 小螺解析并广播到伦敦社区 + 精准推给 5 位标注「熟悉本地生活」的响应者 → 30 分钟无人应答，小螺用社区历史语料兜底作答
- S5 突发：护照丢了、生病、被警察拦下语言不通 → 应急求助卡（当地语言 + 步骤 + 使领馆信息）+ 同城响应者优先推送
- S6 临时：今晚拼饭 / 拼车去希思罗

**平台侧**

- S7 供给上线：选择城市 → 勾选能力标签（带路/拍照/翻译/代购/闲置转让）→ 验证 `.edu` 邮箱 → 进入城市响应池 → 收到匹配的需求卡片

## 4. 需求范围与优先级

**P0（V2.0 必须做，构成主干闭环）**：需求单发布（含 AI 解析）、需求单状态机、响应与选定、双向评价、城市社区与响应池、四层信任体系基础版、安全体系（拉黑/举报/行程报备/仅同性响应）、分级审核、小螺 L0/L1、消息通知。

**P1（V2.0 做，体验杠杆高）**：小螺 L2 自动分发、AI 行程与落地清单、小红书图文生成、应急求助卡、内容→需求单一键转化、需求单二次投放、会员体系、信任分展示、小组健康度。

**P2（V3.0 及以后）**：本地商家入驻位、长期搭子预约、跨城联动、多语言界面、争议仲裁流程化、供给端认证徽章年费、担保交易（需主体与牌照条件成熟）。

## 5. 核心机制设计

### 5.1 需求单（Request）：产品的原子单位

一个有明确诉求、明确时效、可被接受、可被完成、可被评价的对象。所有内容型帖子降级为社区内容，服务于供给端入驻与 AI 知识库。

| 字段 | 必填 | 说明 |
|---|---|---|
| 品类 category | 是 | 8 类白名单（见 5.6） |
| 城市 city | 是 | 绑定城市社区，决定分发范围 |
| 标题 title | 是 | ≤20 字，可由 AI 生成 |
| 详情 detail | 是 | 自由文本 + 图片 ≤9 张 |
| 时效类型 timing | 是 | 预约型（含起止时间）/ 即时型（1h / 3h / 今天内） |
| 期望时间 expect_time | 预约型必填 | 日期 + 时段 |
| 地点范围 area | 否 | 模糊到街区级，**不精确到门牌**（安全设计） |
| 报酬类型 reward_type | 是 | 免费互助 / 请一顿 / 付费（金额区间）/ 以物换物 |
| 参考金额 amount | 付费时必填 | 仅作线下协商参考，平台不代收 |
| 人数 headcount | 搭子类必填 | 1~N |
| 偏好 preference | 否 | 语言、仅同性响应（安全开关）、是否需认证响应者 |
| 可见范围 visibility | 是 | 城市社区公开 / 指定小组 / 仅定向邀请 |

**状态机**

```
草稿 Draft
  └─发布→ 招募中 Open ──有人响应→ 待选定 Responded
                                    ├─选定→ 已确定 Matched（双方互相下发联系方式）
                                    │         ├─双方确认→ 已完成 Done →互评→ 已评价 Rated
                                    │         ├─需求方撤销选定→ 回到 待选定（原响应全部保留）
                                    │         └─任一方取消→ 已取消 Cancelled（记录取消方）
                                    └─超时无选定→ 已过期 Expired
  └─有效期到/超时无响应→ 已过期 Expired ──→ AI 兜底作答 / 归档进城市知识库
  └─违规→ 已下架 Removed
```

**关键规则**

1. **需求单必然会终结**。预约型在期望时间后 24h 自动过期，即时型按有效时长过期。不存在永久挂着的需求。
2. **过期不等于浪费**。过期需求单连同响应内容进入城市知识库，成为小螺 RAG 的语料。稀疏期的失败也在积累资产。
3. **取消与撤销留痕，但不作为信任分的主要输入**。信任分主要看双方交易后的真实互评。理由：交换联系方式后线下沟通失败、改变主意、同时聊几个人都属正常行为，按次数扣分是在惩罚正常行为，还会诱导用户不点取消、把单子挂到过期（更坏的结果）。
4. **选定可撤销**。需求方可从「已确定」退回「待选定」重新挑人，原响应保留；**但已交换的联系方式无法收回**，撤销时必须明示。
5. **同城同时在架上限**：免费用户 3 条，会员 10 条。

### 5.2 撮合流程

```
需求方                        平台/小螺                      本地响应者
  ├─ 一句话说出诉求 ────────────▶ AI 解析成结构化需求单
  │  ◀── 预填表单，用户确认/修改 ─┤
  ├─ 发布 ──────────────────────▶ 机审（毫秒级）
  │                              ├─ 命中风险→转人工，否则直接可见
  │                              ├─ 分发：① 城市广场展示
  │                              │        ② 精准推送（订阅消息）───▶ 收到需求卡片
  │                              │        ③ 广播到相关小组
  │  ◀── 响应列表（含信任档案）───┤◀──────────────────────────────┤ 响应（一句话 + 报价）
  ├─ 选定 1 位 ─────────────────▶ 生成约定单 + 下发联系方式 ─────▶ 收到选定通知
  ├─────────── 线下完成，双方各自点击「已完成」──────────────────┤
  │                              ├─ 双向评价（互评前互不可见）
  │                              └─ 更新信任分 / 沉淀城市知识库
  │              ※ 2 小时无响应 → 小螺二次改写投放（≤2 次）
  │              ※ 仍无响应 → 小螺基于城市知识库兜底作答
```

**约定单（Agreement）**：选定后自动生成的只读卡片，字段为「谁、什么时间、在哪、做什么、约定报酬多少、线下如何支付」。双方均可见、不可单方修改（修改需双方重新确认并留版本记录）。它替代 V1.0 的「担保交易」——**平台托管的是共识与凭证，不是钱**。发生纠纷时，约定单 + 聊天记录 + 评价构成判定依据，处理结果体现为信任分与封禁，而非退款。

### 5.3 城市社区：供给的容器

**城市是唯一的一级容器，小组是城市下的二级分区。**

- 城市（官方维护，全球开放浏览，运营重点为伦敦）
  - 官方分区（每城固定 5 个，与需求单品类对齐）：找搭子、问本地、跑腿代购、闲置转让、住宿
  - 兴趣小组（用户可申请创建，受健康度约束）

**小组健康度**：每周按「周活跃发帖人数、需求单产生数、首响率、成员留存」算分。≥60 正常展示；30~60 降权并提示组长发起话题（小螺可代写）；连续 3 周 <30 进入沉寂，停止新成员进入、内容合并到官方分区、小组归档。

**建组数量上限** = 该城市周活跃用户数 ÷ 20（向下取整），伦敦初期即 0~2 个。**这条是有意的克制**：冷启动期把流量按住在官方分区，不允许提前碎片化。

**开城标准**（四项同时满足才复制下一城）：认证本地响应者 ≥50 人、周需求单 ≥30 条、首响率 ≥60%、响应者次月留存 ≥40%。理由：撮合是密度游戏，个人开发者的运营带宽只够一座城，3 城试点等于把密度除以 3。

**冷启动渠道用学校，产品结构用城市。** 旅行者只知道城市不知道学校，所以容器必须是城市；但留学生天然按学校组织，所以 BD 动作按学校推进（伦敦首批 UCL / KCL / IC / LSE）。这两件事不矛盾。

### 5.4 反死水机制

V1.0 只有三条规则，V2.0 从五个层面同时施压：

1. **需求层**：需求单强制有时效并自动过期，社区里永远只陈列「还有效的事」
2. **分发层**：不依赖用户主动刷，靠精准推送 + 小组广播 + 二次改写投放把需求送到人面前
3. **容器层**：小组健康度 + 建组上限，冷启动期强制流量收拢
4. **兜底层**：无人响应时 AI 直接作答，把「发了没人理」的流失挽回
5. **运营层**：每日城市话题机器人、每周精华摘要、组长激励、学校 BD

配套**内容播种**：伦敦上线前预置 30 条高质量社区内容 + 100 条问答语料，同时作为小螺的初始知识库。**冷启动期的社区可以是人工的，但不能是空的。**

### 5.5 信任体系：四层信任，不收证件

**核心取舍**：既要低门槛入驻，又要有安全保证。解法不是把认证做强，而是**放弃「已认证/未认证」的二元标签，改为「信任分档 + 证据清单」，并把强制校验推迟到高风险动作发生的那一刻**。

**为什么不收证件**：护照、签证、学生证属身份证件类敏感个人信息。GDPR 下处理这类数据需要明确的合法性基础、数据保护影响评估、加密存储与最小化留存，个人开发者不具备承担这一责任的能力，一次泄露的后果远大于产品收益。因此 V2.0 **完全不采集证件影像**。

| 层 | 名称 | 获取方式 | 需资质 | 可信度 |
|---|---|---|---|---|
| L1 | 基础身份 | 微信授权登录 + 常驻城市自选 + 性别自填（可留空） | 无 | 低 |
| L2 | 自证 | ① `.edu`/学校邮箱验证码（只存"已验证 + 学校名"）② 社媒绑定 ③ 自我介绍完整度 | 无 | 中 |
| L3 | 履约 | 真实完成单数、双向评价、平均响应时长、被举报率 | 无 | **高** |
| L4 | 社区背书 | 组长/老用户背书（每人每月限 2 次，被背书者违规则背书人连带扣分） | 无 | 高 |

**不采集手机号**：微信的手机号快速验证接口对个人主体小程序不开放；自建短信通道面向海外号码成本与合规都不划算。云函数拿到的 openid 本身就是微信校验过的可信身份，手机号在本产品里不额外提供可信度，去掉它同时符合数据最小化。

**性别字段的用途只有一个**：支撑「仅同性响应」安全开关。自填、可留空、不校验；未填性别的用户不能响应设了该开关的需求单（提示补全即可解锁）。除此之外性别不参与任何排序、推荐或筛选，**不提供任何异性偏好选项**。

**社媒绑定的零资质方案**：用户提交小红书/Instagram 主页链接，平台生成一次性口令要求临时加进个人简介，校验后**只存「已绑定 + 主页 URL + 校验时间」**，不抓取、不存储对方平台内容。零成本、零资质、可随时解绑。

**信任分（0~100）**

- 构成：L1 基础 10 分 + L2 自证 ≤20 分 + L3 履约 ≤60 分 + L4 背书 ≤10 分
- **L3 的主要输入是双方交易后的真实互评**，其次是真实完成单数；取消率、撤销次数只作为风控信号参与小幅调整
- 展示形态：**不显示裸分数**，显示四档徽章（新面孔 / 靠谱 / 老手 / 城市之光）+ 可展开的证据清单（"已完成 12 单｜好评率 100%｜平均 18 分钟响应｜UCL 邮箱已验证"）
- 关键原则：**让用户看到「他凭什么可信」，而不是一个不可解释的分数**。分数不可解释会同时打击被评者的积极性和求助者的信心。

**强制校验点（只在这三处拦截）**

1. 接「付费地陪 / 翻译陪同」→ 需 L2 完成 + 信任分 ≥40
2. 发布或接「住宿」→ 需 L2 完成 + 至少 1 条历史好评
3. 首次发起 1v1 线下见面确认 → 强制阅读安全提示并勾选

**降低警惕的产品手法**：增信引导不用「为了安全请认证」（暗示危险），而用「补全后被选中的概率高 2.6 倍」（收益框架），并让高信任分用户在响应列表天然靠前——让增信的动机来自竞争而非恐惧。

### 5.6 安全体系（P0）

这是一个促成陌生人在异国线下见面的产品，安全是核心差异化而非附加项。

**事前**：仅同性响应开关（默认关闭，女性用户首次发单时主动提示）｜地点模糊化（只到街区/地铁站级，疑似门牌地址做提示拦截）｜安全提示卡（选定后强制展示一次：首次见面选公共场所、不提前转账、不交出证件、告知朋友行程）｜住宿类要求双方均 L2 完成并展示独立安全须知

**事中**：行程报备（一键生成行程卡片，通过微信分享给指定联系人或群；**不在后台存储「紧急联系人」字段**，避免采集第三方个人信息）｜一键 SOS（当地紧急号码按城市配置：英国 999、欧盟 112、美国 911；+ 中国使领馆电话 + 一键把行程卡片发给此前报备的联系人）｜反诈风险提示（私信出现"先转账""押金""发身份证照片""退出平台交易"等模式时，**向双方**弹出提示，避免误伤正常沟通）

**事后**：双向评价（互评前互不可见，7 天未评视为默认好评但不计入好评率）｜拉黑（互相不可见需求单、不可响应、不可私信）｜举报（六类：人身安全 / 擦边交友 / 诈骗 / 引流 / 违规内容 / 未履约，人身安全类进最高优先级队列并直接冻结被举报人接单能力）｜处罚阶梯（提示 → 限流 → 禁止接单 7 天 → 永久封禁）

**联系方式交换**：由用户在「我的」里自填（微信号/电话/其他），**发布需求时不需要也不允许挂在需求单上**——那等于向全城公开个人账号。只在需求单进入「已确定」之后、在需求方与被选定的响应者之间双向下发，其他任何身份、任何状态都拿不到。用户可随时清空，清空只对之后新达成共识的人生效，已经看到的收不回，界面如实说明。

### 5.7 内容治理与分级审核

| 用户/内容分级 | 策略 |
|---|---|
| 新用户前 3 条内容、或信任分 <30 | 机审 + 人工复核后可见（目标 30 分钟内） |
| 信任分 ≥30 且无违规记录 | 机审通过即可见，**先发后审** |
| 敏感品类（住宿、应急求助、含金额的付费单） | 一律机审 + 人工抽检 |
| 命中高风险语义 | 直接拦截，不可发布，给出可修改提示 |

机审毫秒级由 AI 承担；人工复核在小程序内的管理员页面处理，配合「待审队列 + 一键通过/驳回模板」，目标每日 <20 分钟。

**反擦边交友治理**

1. **品类白名单**：只有 8 个品类——搭子同行 / 付费地陪 / 借物易物 / 住宿 / 打听咨询 / 代购跑腿 / 翻译陪同 / 应急求助。没有「交友」「同城」「聊天」选项，无法归入 8 类的需求无法发布。
2. **语义识别拦截**："仅限异性""看颜值""长期关系""有偿陪伴"及其变体、谐音、拼音缩写。
3. **偏好字段单向可用**：性别偏好只能用于「仅同性响应」，**不提供「仅异性响应」**——从数据结构层面消灭擦边需求。
4. **举报独立分类**：「擦边交友」为一级举报类型，优先级仅次于人身安全。
5. **处罚从重**：跳过提示，直接禁止接单 7 天，二次永久封禁。

治理原则写进社区规范首屏：**喊呗解决的是「办事」，不是「处对象」。** 让规则以产品价值观的方式表达，比藏在协议里有效。

## 6. AI 能力设计

### 6.1 战略定位

**在喊呗里，AI 不是效率工具，AI 是供给的兜底层。**

推导：本产品最致命的流失点不是「匹配不精准」，而是「发了需求没人理，用户当天就走了」——旅行者在当地只停留几天，这类流失不可挽回。冷启动期供给必然稀疏，运营短期解决不了。因此 AI 的第一价值不是提效，而是**在真人供给缺席时先把这个用户的需求兜住**。

三条 AI 产品原则：

1. **AI 是供给的兜底层，不是替代层**。真人响应永远优先展示，AI 答案只在无响应或用户主动询问时出现，且明确标注来源。
2. **AI 承担「从模糊到结构化」的翻译工作**。用户不需要学会填表，这是需求方门槛降到最低的唯一办法。
3. **AI 的自主性由用户选择，而非由产品单方决定**。

**数据飞轮**：社区内容 + 历史需求单 + 真人回答 → 按城市分片入库 → 小螺 RAG 质量提升 → 兜底答案更有用 → 用户留存 → 更多需求单与回答 → 语料继续增长。

**喊呗的 AI 护城河不在模型，在城市语料。** 同一个模型，有伦敦三年问答语料的产品和没有的产品，输出质量完全不同。这也解释了为什么必须单城做深——语料密度和撮合密度是同一件事。

### 6.2 「小螺」能力地图

形态：**底层能力 + 对话式助手入口双轨**。底层能力隐形嵌在发布、匹配、审核链路里（用户感知不到 AI，只感知到「变简单了」）；对话入口承载复杂意图与兜底问答。

| # | 工具 | 触发位置 | 优先级 |
|---|---|---|---|
| 1 | `parseRequest` 一句话→结构化需求单 | 发布页顶部输入框、助手对话 | P0 |
| 2 | `createRequest` 确认后创建需求单 | 助手对话 | P0 |
| 3 | `searchKnowledge` 城市语料检索 | 兜底作答、助手问答 | P0 |
| 4 | `matchResponders` 匹配响应者 + 生成推荐理由 | 需求单发布后 | P1 |
| 5 | `draftInvite` 生成定向邀请文案 | L1 一键代发 | P1 |
| 6 | `broadcast` 分发到城市/小组 + 二次改写投放 | L2 自动分发 | P1 |
| 7 | `generateChecklist` 落地清单 / 行程建议 | 助手对话、需求单详情 | P1 |
| 8 | `moderate` 内容风险分级 | 所有 UGC 提交时 | P0 |
| 9 | `riskHint` 私信反诈提示 | 私信会话 | P0 |
| 10 | `generateXhsPost` 小红书图文生成 | 完成需求单后、我的-作品 | P1 |
| 11 | `emergencyCard` 应急求助卡（当地语言） | SOS、应急求助品类 | P1 |
| 12 | `dailyTopic` 城市话题 / 周精华摘要 | 定时任务 | P1 |
| 13 | `summarizeReviews` 评价聚合成信任标签 | 个人主页 | P2 |
| 14 | `translate` 短文本翻译与破冰话术 | 私信 | P2 |

**关于 #10 的诚实定义**：命名为「生成小红书图文」而**不是**「同步到小红书」。产品行为是生成封面图（模板套图，非 AI 绘图）+ 正文文案 + 话题标签 → 一键复制 + 批量存图 → 提示用户手动打开小红书发布。小红书没有开放给第三方的发布接口，任何声称「一键同步」的产品实质都是这套流程。**在 PRD 里把技术不可行的地方写清楚，比留一个做不出来的需求更负责。**

**关于 #11 应急求助卡**：按城市预置结构化模板（丢护照/生病/被盗/交通事故/语言不通），输出 = 处置步骤 + 当地语言短句大字卡片 + 使领馆与紧急号码。事实性内容来自预置结构化数据，模型只负责组织与翻译——**高风险场景不让模型编事实**。

### 6.3 自主性阶梯：把「该不该自动」变成用户可选的产品维度

这是本产品 AI 设计的核心主张。全自动有风险、纯手动没价值，正确答案不是在两者之间取折中点，而是**把自主性本身产品化为一个可解释、可调节、可回退的档位**，默认值保守，由用户按信任程度自行上调。

| 档位 | 名称 | 可做 | 不可做 | 默认对象 |
|---|---|---|---|---|
| **L0** | 只读建议 | 解析需求、给攻略与清单、答疑 | 不对外发送任何内容 | 新用户前 3 单 |
| **L1** | 一键代发 | 生成邀请文案 + 候选人名单，等你勾选后统一发出 | 不自动发送 | **全局默认档** |
| **L2** | 自动分发 | 发布后自动向匹配响应者推送**结构化需求卡片**；2h 无响应自动改写文案二次投放（≤2 次） | 不进 1v1 私信、不模拟真人语气、不代答追问 | 用户手动开启 |
| **L3** | 自动协商 | —— | **本产品不做** | 不提供 |

**L2 的形态约束很关键**：对外触达只能是「系统需求卡片」，视觉上明确是卡片而非聊天气泡，并强制带「由小螺代为分发」标识。这样既拿到自动分发的效率，又不产生「AI 冒充真人」的问题。

**为什么不做 L3**（写入 Roadmap 的「明确不做」，并把理由展示给用户）：

1. **责任无法归属**。AI 谈定的见面时间地点若发生人身安全事件，责任链条不清。
2. **AI 承诺会造成真实损失**。谈价、谈时间属于对现实世界的承诺，模型出错的代价由用户承担。
3. **伦理与合规**。AI 以真人语气与人协商却不明示身份，在多数地区已属需要披露的行为。
4. **能力边界诚实**。个人开发者无力承担由此产生的纠纷处理与客服成本。

**L1 → L2 的引导设计**：不在设置页里藏一个开关等用户发现，而是在「L1 发送邀请后获得响应」这个正反馈时刻提示："下次要不要让小螺自动帮你喊人？"——在信任已建立的时刻请求更多授权。

### 6.4 护栏与红线

| 类别 | 规则 |
|---|---|
| 身份明示 | Agent 产出的一切对外内容强制带「AI 协助」标识，助手对话首屏声明"我是 AI" |
| 四类字段禁止代填 | 金额、见面时间、见面地点、联系方式——只能留空，必须由人填写 |
| 频控 | 同一响应者每日被 Agent 触达 ≤3 次；被静默或拒绝 2 次后进入 7 天冷却 |
| 事实性边界 | 签证、医疗、法律、移民问题**在服务端前置拦截**，不调模型、不占额度，给出官方链接 |
| 来源标注 | 兜底答案必须标注来源（"根据伦敦小组 3 条历史回答，请自行核实"） |
| 追问上限 | 解析失败最多追问 2 轮，之后降级为普通表单，禁止死循环 |
| 可解释性 | 每条推荐必须给出依据字段（城市匹配/能力标签/完成单数/响应速度），不允许「猜你喜欢」式无理由推荐 |
| 可回退 | 任何 AI 生成内容均可一键改为手动编辑；L2 可随时关闭且立即生效 |

### 6.5 AI 评测指标

AI 功能必须可度量，否则无法判断该不该继续投入。

| 能力 | 指标 | 达标线 |
|---|---|---|
| 需求单解析 | 字段抽取准确率 | ≥85% |
| 需求单解析 | 用户提交前的字段修改率 | ≤30% |
| 需求单解析 | 发布转化率提升（vs 纯表单，A/B） | +20% |
| 智能分发 L2 | 需求单首响率提升（A/B） | +30% |
| 智能分发 | 响应者被打扰投诉率 | ≤2% |
| 兜底作答 | 采纳率（点「有用」或未继续追问） | ≥50% |
| 兜底作答 | 无响应需求单的当日留存挽回率 | ≥25% |
| 机审 | 违规漏放率 / 正常内容误杀率 | ≤3% / ≤5% |
| 小红书图文 | 生成后实际复制/存图率 | ≥40% |
| 全局 | 每次成功撮合的 AI token 成本 | ≤0.10 元 |

**分阶段验证**：带「A/B」的三项依赖真实流量，在有真实用户之前无法验证，推后到 M5。当前阶段改用**离线评测集**证明 AI 质量：36 条真实语料的人工黄金标注 + 评测脚本。**首轮基线：字段抽取准确率 89.2%，四类禁填字段误填 0 次。** 这一项不需要任何用户即可度量，也是对外展示 AI 能力最实在的材料。

### 6.6 成本与额度

按国产便宜模型档位（DeepSeek / 豆包 / Qwen-Turbo 级）：需求单解析 0.001~0.005 元/次，机审 <0.001 元，RAG 兜底 0.005~0.02 元，落地清单 0.02~0.05 元，小红书文案 0.005~0.015 元。

结论：**短文本能力完全给得起免费**。日活 500、人均 3 次短文本调用的规模下 AI 月成本在几十元量级。真正贵的是长输出和图像生成——因此小红书图文只做模板套图不做 AI 绘图，行程生成设每日限额。

- **无限免费**：需求单解析、内容转需求单、机审、反诈提示、短文本翻译、评价标签聚合
- **每日限免（免费用户）**：AI 行程与落地清单 1 次/天、小红书图文 1 次/天、L2 自动分发 1 单/天、兜底追问 5 轮/天
- **会员放开**：上述额度 ×10 或不限

**定价原则：不给「AI 调用次数」定价，给「结果」定价。** 会员权益的对外表述是「更快被人响应、更容易被选中」，AI 额度只是实现手段，不作为卖点陈列。一旦让用户按次数计算 AI 成本，付费意愿会立刻崩塌，而且会把产品价值锚定在「AI 工具」而非「撮合服务」上。

```
消息 → 需求单通知 → 详情｜互动通知 → 内容详情｜私信 → 会话
我的 → 我的需求单 → 状态分组（招募中/待选定/进行中/已完成/已过期）
我的 → 信任档案 → 增信任务清单（邮箱验证/社媒绑定/完善介绍）
```

### 7.4 关键页面交互要点

**发布页（最重要的转化页面）**

- 首屏只有一个输入框和一句提示："想找人做什么？一句话说清就行"。**不首屏展示表单**——表单是解析后的结果，不是输入的起点。
- 输入后点「帮我整理」，AI 解析出品类、时效、城市、报酬类型，以卡片展示"我理解成这样，对吗？"，每个字段可点击修改。
- 解析失败或用户跳过 AI → 降级为普通表单，不阻断。
- 金额、见面时间、见面地点三项即使 AI 有推测也留空高亮，提示"这几项请你自己确认"。
- 底部实时展示预期："发出后将推送给伦敦 23 位可能帮上你的人"——**把不可见的分发过程可视化，这是提升发布意愿的关键**。

**需求单详情页（响应者视角）**

- 顶部即为决策所需的全部信息：品类、时效倒计时、报酬、地点范围、需求方信任徽章。
- 响应按钮附带一句话输入与报价输入，把响应成本降到 10 秒内。
- 明确展示「已有 N 人响应」，避免响应者做无效投入。

**响应列表（需求方视角）**

- 每条展示昵称、信任徽章、证据摘要（完成单数/好评率/平均响应时长）、报价、一句话自荐、AI 推荐理由。
- 默认按「信任分 + 响应速度」综合排序，可切换按报价。
- 选定需二次确认并展示安全提示卡，文案必须说清两件事：**选定后双方互相看到联系方式**、**约不上可以撤销选定重新挑人（撤销会被记录，但已看到的联系方式收不回）**。

## 8. 数据与指标

- **北极星**：每周成功撮合数（需求单被接 + 双方确认完成）。同时依赖供需两侧，无法靠单侧刷量做高。
- **护栏 1**：需求单首响率（发布后 2h 内至少 1 条响应），目标 ≥60%。它是撮合数的领先指标，能在撮合完成前就暴露密度问题。
- **护栏 2**：本地响应者次月留存，目标 ≥40%。需求方是流动的（旅行者用完即走），供给方才是留存的根基，供给一旦流失产品立刻回到死水状态。
- **明确不作为核心指标**：DAU、发帖量、小组数量。它们都能靠「看内容」刷出来，与撮合成功无因果关系。

**核心漏斗与各环节目标**

```
进入城市 → 浏览 → 发起需求单 → 获得首响 → 选定 → 线下完成 → 双向评价 → 复用
              ↓ 未发布            ↓ 无响应
       发布转化率（AI 解析优化）  兜底作答挽回率
```

发布转化率 ≥25%、首响率 ≥60%、选定率 ≥80%、完成率 ≥70%、评价率 ≥60%、30 天内二次发单率 ≥20%。

**埋点要求**：需求单全生命周期状态变更、AI 每次调用（能力类型/耗时/token/是否被采纳/是否被修改）、分发触达与响应归因（响应来自推送/社区/邀请/广播哪条路径）、增信任务完成漏斗、安全功能使用率、A/B 分桶标识。

## 9. 商业化

### 9.1 前置结论：不碰资金

平台不代收、不代付、不托管任何用户资金，付费类需求的钱款由双方线下自行结算。这不是妥协而是当前条件下的最优解。相应地，**平台把「担保」从资金担保替换为信誉担保**：托管约定单、沉淀双向评价、留存纠纷证据、以信任分和封禁作为约束手段。这套机制提供了担保交易约 80% 的信任价值，而风险与合规成本接近于零。

### 9.2 四阶段路线

- **阶段 0｜验证期（0~6 个月）：不赚钱。** 唯一目标是把伦敦的每周成功撮合数跑起来。任何收费都会在密度不足时杀死冷启动。
- **阶段 1｜会员订阅（撮合量稳定后）**：向**需求方**收费，卖「更快被响应、更容易被选中」——需求单置顶/加急曝光、在架上限 3→10、查看响应者完整信用档案、高级筛选、AI 高成本能力额度放开、已读回执。定价 ¥18/月 或 ¥88/年。
  **iOS 规避**：小程序内虚拟权益在 iOS 端受平台规则限制，方案是 iOS 端不展示购买入口、仅展示权益说明并引导至安卓端或公众号 H5 完成购买，权益按账号跨端生效。开发前必须确认当期微信与 Apple 规则。
- **阶段 2｜供给端变现（更健康的收入）**：向**本地响应者**收费——认证徽章年费（含人工背景核验与主页展示位）、接单曝光包、个人服务主页（做本地向导 IP）。供给端有真实收益动机，付费意愿显著高于旅行者。
- **阶段 3｜本地商家与生态（天花板最高，且完全不碰资金）**：当地华语商家的城市入驻位与内容推广位（中餐馆、民宿、接送机、驾照代办、搬家），以及留学生活服务 CPA 分成（eSIM、境外保险、换汇、行李托运）。按曝光/线索计费，无资金归集。
- **阶段 4｜担保交易（长期）**：需企业主体、支付资质或持牌第三方合作、专职客服与风控。个人开发者阶段**明确不做**，但数据结构（约定单、金额字段、状态机）预留了升级空间。

### 9.3 单位经济

成本结构：云函数 + 云数据库（月 30~100 元）、AI token（日活 500 量级月几十元）、域名与备案（年百元级）、人工审核（自身时间，目标 <20 分钟/天）。

结论：**月运营成本可控制在 200 元以内**，达到阶段 1 后单城即可覆盖成本。这个数字本身就是「不碰资金 + 用便宜模型 + 单城做深」三个决策的合理性验证。

## 10. 合规与落地路线

### 10.1 核心风险：个人主体无法上线 UGC 社区类小程序

**这是本项目最大的落地障碍，优先级高于任何功能设计。**（以下为截至 2026 年 8 月的公开信息，开发前必须以微信公众平台官方文档再次确认）

- 小程序涉及发帖、评论、动态、私聊、关注等 UGC 与社交功能，需要「社交-社区/论坛」或「社交-笔记」类目。
- 这些类目**不向个人主体开放**，后台入口为灰态，无法提交审核。个人主体小程序实质上只能做无用户互通的工具与信息展示类产品。
- 开通路径：注册企业或个体工商户主体 → 完成 ICP 备案 → 申请对应类目。涉及广告或会员收益则需经营许可证（个人与个体户通常无法办理）。
- 社交、文娱类小程序通常会进入网信部门二次审核，周期一周至一个月。

主体成本区间：个体工商户年综合成本约 500~1500 元；有限公司首年约 3000~8000 元。在「业余时间、投入资金近 0」的约束下，**不建议现在注册主体**。

### 10.2 为什么不碰资金

即使注册了主体，代收代付也不可行：微信支付的跨境结算与境外商户能力需要企业资质与外汇备案；向海外个人账户打款属于持牌的支付/汇款业务；一旦形成预付资金池，将涉及无证经营支付业务的法律风险，且退款纠纷会吞掉个人开发者的全部时间。因此「不碰资金」是长期结论。

### 10.3 落地路线：A + B 双 Demo

**Demo A｜可真实使用的完整版（主线）**

- 完整前端 + 后端 + 数据库，P0 功能全部真实可用，AI 能力接真实模型
- 发布形态：**微信小程序体验版**。体验版无需提交审核即可分享给受邀体验成员使用，因此不受个人主体类目限制。这是零成本、零合规风险、且能获得真实用户数据的唯一路径
- 体验成员有数量上限，因此天然适配「伦敦单城 + 小范围真实运营」的冷启动策略
- 展示方式：真机演示 + 数据看板 + AI 效果数据

**Demo B｜升级路径演示版**

- 演示「如果具备主体与资质，产品会长成什么样」：担保交易流程、本地商家入驻、供给端认证徽章、多城市联动、跨城数据看板
- 形态为高保真交互原型（不接后端），明确标注为「Roadmap 演示」
- 价值在于展示完整的商业推演能力，同时诚实标注当前不可落地的原因

**升级触发条件**：伦敦达到阶段 1 的收入验证（或有明确融资/合作意图）时，再启动主体注册 → ICP 备案 → 类目申请 → 正式发布。届时 Demo A 的代码与数据可直接迁移。

### 10.4 其他合规事项

- **GDPR**（用户主要位于欧盟/英国）：提供独立可访问的隐私政策与用户协议、明确数据用途与保留期、提供账号与数据删除入口。**不采集证件影像、不采集精确位置、不采集第三方联系人信息。**
- **数据最小化**：位置只到城市与街区级；社媒绑定只存 URL 与校验结论；邮箱验证只存「已验证 + 学校名」。
- **UGC 基础四件套**（无论何种发布形态都必须具备）：内容风控与语义拦截、举报与拉黑入口、独立的隐私政策与用户协议页、明确的社区规范。
- **未成年人**：注册要求 18 岁以上，需求单中涉及未成年人陪同的直接拦截。

## 11. 技术实现约束

技术选择服从两个原则：**能力够用即可，且不引入需要持续付费或运维的组件。**

| 环节 | 方案 | 说明 |
|---|---|---|
| 前端 | 微信小程序原生 | 不用 Taro / uni-app：只有一个交付端，跨端能力用不上 |
| 后端与数据库 | 微信云开发（云函数 + 云数据库 + 云存储） | 免服务器运维、有免费额度、与小程序鉴权天然打通 |
| 1v1 私信 | 云数据库轮询 + 实时数据推送 | **不自建 WebSocket**，实时性可放宽到秒级 |
| 消息触达 | 微信订阅消息（一次性订阅） | 免费。**一次授权对应一条推送**，因此每次发布需求单/收到响应时都要顺势请求授权——这是产品设计必须配合的技术限制 |
| AI 调用 | 云函数代理调用模型 API | 密钥不落前端；统一做频控、额度、缓存、成本统计。只讲 OpenAI 兼容协议，换供应商等于改三个环境变量 |
| RAG | 城市语料分片检索，**起步用关键词 + 标签过滤，暂不上向量库** | 冷启动期语料只有几百条，向量检索的质量提升观察不到，却多一个必须维护同步的组件。升级触发条件：单城语料 >2000 条，或兜底采纳率 <50% |
| 图片 | 云存储 + 端侧压缩 | 上传前压缩，控制存储成本 |
| 运营后台 | **小程序内的管理员页面**（openid 白名单 + 云函数二次校验） | 只做待审队列、举报队列、用户管理、数据看板四件事，不做独立 Web 后台 |
| A/B 与埋点 | 云函数配置表 + 自建埋点集合 | 不引入第三方分析 SDK |

**服务端边界**：数据库权限收成「所有用户不可读写」——端侧读写全部被拒，一切数据访问只能走云函数；状态变更一律走事务，状态与审计日志同生共死。

**已实现的服务端构成**：7 个云函数（`login` 登录建档 / `requestFlow` 发布与完成 / `responseFlow` 响应与选定 / `aiGateway` 全项目唯一模型出口 / `moderation` 三层内容安全 / `track` 埋点 / `cron` 定时任务）+ 10 个集合。

**明确的技术不可行项**（写入文档避免后续返工）

1. 小红书内容同步：无开放发布 API，只能生成内容 + 复制 + 引导手动发布
2. 小程序无法直接跳转外部 App：无法一键打开小红书，只能复制到剪贴板
3. 主动推送：不存在无授权的主动推送能力，只能依赖订阅消息，因此 L2 自动分发的触达率上限受用户授权率约束
4. 精准定位：境外定位精度与授权率均低于国内，因此城市采用「自动定位 + 手动选择」双轨，且**所有逻辑以手动选择为准**

## 12. 运营与冷启动

**第 0 步：上线前把社区填满（不能空着）** —— 预置 30 条高质量社区内容（换电话卡、机场交通、退税、看病、报警、便宜超市、中餐推荐、地铁卡、租房避坑、常见诈骗）+ 100 条问答语料作为小螺初始知识库 + 5 个官方分区与规范首屏。

**第 1 步：先攒供给（学校为抓手）** —— 目标 50 位认证本地响应者。渠道是 UCL/KCL/IC/LSE 的学生会、新生群、二手群、校友会，以及小红书上活跃的伦敦留学生博主。话术切入点是收入与轻松感而不是「来做志愿者」："周末带人逛一天，赚顿饭钱 + 攒信用"。冷启动激励零成本：首批 50 人授予「创始响应者」永久徽章 + 名录永久优先展示位——**用身份和曝光换供给，不用现金**。

**第 2 步：再引需求（小红书为主战场）** —— 内容形态是「我在伦敦喊了一声，真有人来了」的真实案例图文（这正是「生成小红书图文」能力存在的运营理由：把用户的每次成功撮合变成获客素材）。关键词布局：伦敦搭子、伦敦一日游、伦敦地陪、伦敦拍照、留学生二手。转化路径：小红书图文 → 评论区/主页引导 → 小程序体验版二维码。

**持续运营（每日 <30 分钟）**：小螺自动生成每日城市话题与每周精华摘要（组长只需确认发布）｜待审与举报队列（<20 分钟/天）｜每周复盘三个数（成功撮合数、首响率、响应者留存）｜对无人响应的需求单人工兜底一次（既是留存挽回也是语料积累）。

## 附录 A：术语表

- **需求单（Request）**：产品的原子单位。一个有明确诉求、明确时效、可被接受、可被完成、可被评价的对象。
- **约定单（Agreement）**：选定响应者后自动生成的只读共识凭证。平台托管共识，不托管资金。
- **本地响应者**：当地常驻的华人/留学生/长期旅居者，构成城市供给池。
- **喊呗信任分**：由基础身份、自证、履约、社区背书四层构成的 0~100 分值，对外展示为四档徽章 + 证据清单。
- **小螺**：产品内 AI 助手的名称，同时是底层 AI 能力的统称。
- **自主性阶梯（L0~L3）**：小螺对外行动权限的四个档位，由用户选择，默认 L1，L3 不提供。
- **兜底作答**：需求单无真人响应时，小螺基于城市语料给出的答案，明确标注来源与「请核实」。
- **小组健康度**：城市下兴趣小组的周度评分，低于阈值将被降权、合并或归档。
- **开城标准**：复制到下一座城市前必须同时满足的四项量化门槛。

## 附录 B：开发前必须逐项核实

任何一项的结论变化都会影响方案：

7. 所选模型 API 的当期价格与并发限制，据此复核成本估算
8. 是否需要为体验版用户提供独立的数据删除与导出入口
